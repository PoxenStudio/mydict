# MyDict 代码规范

版本：v1.0
日期：2026-09-10

---

## 1. 通用约定

- **Git 分支模型**：`main` 为受保护分支（始终可部署）；功能开发用 `feature/xxx`，修复用 `fix/xxx`，紧急修复 `hotfix/xxx`。
- **Commit 规范**：采用 [Conventional Commits](https://www.conventionalcommits.org/)，格式 `<type>(<scope>): <subject>`：
  - `feat` 新功能、`fix` 修复、`docs` 文档、`style` 纯样式/格式（不影响逻辑）、`refactor` 重构、`perf` 性能优化、`test` 测试、`chore` 构建/工具链变更。
  - 示例：`feat(admin): 支持词典拖拽排序`、`fix(vocab): 修复 Token 收藏重复归属用户的问题`。
- **接口变更同步**：任何 API 新增/修改必须同步更新《技术方案设计.md》第 4 节的接口表，不允许代码与文档脱节。
- **禁止硬编码**：颜色、间距、圆角、阴影等视觉相关的值一律使用《UI设计规范.md》定义的 Design Token（CSS 变量），不得在组件里直接写死 `#2FBF8F`、`12px` 这类数值（一次性、非语义的特殊值除外，需在代码注释里说明原因）。
- **注释**: 不要出现冗长的注释，除复杂逻辑外尽量减少注释。注释中不要引用doc下的文档。

## 2. 前端规范（Vue 3 + TypeScript）

### 2.1 目录结构

```
frontend/src/
├── api/            # 按领域拆分的接口封装（auth.ts / dict.ts / vocab.ts / admin/*.ts），统一走 request.ts 里的 axios 实例
├── assets/         # 图标、静态图片
├── components/     # 可复用展示型组件（PascalCase 文件名，如 WordCard.vue）
├── composables/    # 组合式函数（useXxx 命名，如 useTheme.ts、useAuth.ts）
├── stores/         # Pinia store，按领域拆分（auth.ts / settings.ts / vocab.ts）
├── styles/         # 全局样式与 Design Token（见 技术方案设计.md「结构化样式定义」）
├── views/           # 路由页面级组件，与路由表一一对应
├── router/          # 路由定义，前台/后台分组，后台路由带 meta.requiresAdmin
├── types/           # 全局 TS 类型/接口定义
└── utils/           # 通用工具函数
```

### 2.2 组件与命名

- 强制使用 `<script setup lang="ts">` 组合式 API，不与 Options API 混用。
- 组件文件名、组件名均为 **PascalCase**（如 `VocabList.vue`）；组合式函数 **useXxx** camelCase；变量/函数 **camelCase**；常量 **UPPER_SNAKE_CASE**；TS 类型/接口 **PascalCase**，接口可选前缀 `I`（团队内统一即可，默认不加前缀）。
- 单文件组件内块顺序固定：`<script setup>` → `<template>` → `<style scoped>`，样式默认 `scoped`，禁止无 `scoped` 的全局样式散落在业务组件里（全局样式只允许出现在 `styles/` 目录）。
- Props/Emits 必须显式声明类型（`defineProps<T>()` / `defineEmits<T>()`），禁止使用运行时声明+无类型的写法。

### 2.3 状态管理

- 使用 Pinia，按领域拆分 store（不搞一个巨大的全局 store）；store 内部异步请求统一调用 `api/` 层，不在 store 里直接写 axios 调用细节。
- 组件内非跨页面共享的临时状态优先用组件内 `ref`/`reactive`，不滥用全局 store。

### 2.4 API 调用

- 所有后端接口调用集中在 `src/api/`，基于统一的 axios 实例（`request.ts`）：
  - 请求拦截器自动附加 JWT（登录用户）。
  - 响应拦截器统一处理：`401` 跳转登录、`403` 提示无权限、`429` 提示"操作过于频繁"、其它错误码统一从后端 `{code, message}` 结构里取 `message` 做 Toast 提示。
- 组件里不直接 `import axios`，一律通过 `api/xxx.ts` 导出的函数调用。

### 2.5 样式与主题

- 遵循《UI设计规范.md》与《技术方案设计.md》的结构化样式定义，组件样式只消费 `var(--token-name)`，不重复定义色值。
- 深浅主题切换逻辑统一封装在 `composables/useTheme.ts`，组件不自行读写 `localStorage`/`document.documentElement`。

### 2.6 Lint / Format

- ESLint（`@vue/eslint-config-typescript` + `eslint-plugin-vue` 推荐规则）+ Prettier，提交前本地跑 `npm run lint` 与 `npm run format`；有条件时接入 CI 强制检查、也可用 Git pre-commit hook（如 `lint-staged`）本地拦截。
- TypeScript 开启 `strict` 模式，禁止未处理的 `any`（确需使用需加注释说明原因）。

## 3. 后端规范（Python 3.12 + FastAPI）

### 3.1 目录结构

```
backend/app/
├── api/              # 路由层：仅做参数校验、鉴权依赖注入、调用 service，不直接写业务逻辑/SQL
│   ├── v1/            # 对外查询/收藏 API（第三方 Token 鉴权）
│   ├── web/            # 前台用户 API
│   └── admin/           # 管理后台 API
├── services/          # 业务逻辑层（词典导入、限流计数、统计聚合等）
├── parsers/            # 词典解析器：mdict.py / stardict.py / ecdict.py，统一实现 DictionaryParser 接口
├── models/              # SQLAlchemy ORM 模型
├── schemas/              # Pydantic 请求/响应模型，与 models 严格分离，不复用同一个类
├── core/                  # 配置加载、安全（JWT/密码哈希）、依赖注入、异常定义
├── tasks/                  # APScheduler 定时任务（统计聚合等）
├── cli.py                   # 管理命令行（如 reset-admin-password）
└── main.py                   # FastAPI 应用入口，路由挂载、StaticFiles 挂载
```

### 3.2 代码风格

- 遵循 PEP 8，强制类型标注（函数签名、类属性），用 `black` 统一格式化、`ruff`（含 import 排序规则）做 lint，两者纳入本地/CI 检查。
- 命名：函数/变量/模块 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE_CASE`。
- 路由函数保持精简：参数校验交给 Pydantic schema，权限校验交给 FastAPI 依赖注入（`Depends(require_admin)` 等），业务逻辑一律下沉到 `services/`。

### 3.3 数据层

- 所有表结构变更必须通过 Alembic migration 提交，禁止手工改数据库文件；migration 文件需提交进版本库、命名包含变更摘要。
- `models/` 中的 ORM 类与 `schemas/` 中的 Pydantic 类严格分离：API 输入输出走 schema，数据库交互走 model，两者之间在 service 层做转换。

### 3.4 异常与响应格式

- 统一异常基类（如 `AppError`），各类业务异常（`TokenDisabledError`、`RateLimitedError` 等）继承它；在 `main.py` 注册全局 exception handler，统一输出 `{"code": "...", "message": "...", "detail": null}` 格式的错误响应，前后端约定一致的错误码表。

### 3.5 测试

- 使用 `pytest`；`parsers/`（词典解析）与 `services/`（限流、统计聚合等核心逻辑）需要单元测试覆盖；关键 API（登录、查询、Token 鉴权、收藏增删）需要集成测试（`httpx.AsyncClient` + 测试用临时 SQLite）。

### 3.6 日志与审计

- 应用运行日志使用标准 `logging`，生产环境结构化输出（JSON 格式，便于后续接入日志采集）；**审计日志（`audit_logs` 表）是业务数据，不等同于应用运行日志**，由 service 层显式写入，不依赖日志采集去"猜"发生了什么操作。

## 4. 代码评审与合并

- 合并进 `main` 前需通过：Lint/Format 检查通过、关键路径测试通过、（团队多人协作时）至少一人 Review；个人独立开发场景下，Review 环节替换为自查 checklist（对照本文档 + 《技术方案设计.md》接口/数据模型是否一致）。
- PR/提交描述需说明"做了什么、为什么"，避免只有 `fix bug` 这类无信息量的描述。

---

本规范与《UI设计规范.md》共同构成开发阶段的约束依据，代码审查/自查时以两份文档为准绳；如实践中发现规则不合理，应先更新文档再改变做法，保持"文档即约定"的一致性。
