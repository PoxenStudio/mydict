版本：v1.53（**发音方案切换：去掉服务端 Speex 转码，改为前端 JS 解码**。此前认为
「浏览器都不支持 .spx，必须转成 mp3」——前半句对（Chrome/Safari/Firefox 的原生解码器
都没有 Speex），后半句不对：libspeex 可以编译成 JavaScript 在浏览器里解，django-mdict
项目正是这么做的（`speex.min.js` + `bitstring.min.js` + `pcmdata.min.js` 共约 320KB，
链路是 XHR 拿 spx 字节 → Ogg demux → `Speex.parseHeader` 取 mode/rate/声道 → 解出 PCM →
`PCMData.encode` 合成 WAV Blob → 原生 `<audio>` 播放，连 Web Audio API 都不用），实测
可用。改为同样的路线：解码器三件套随前端静态资源分发（`frontend/public/speex/`，
libspeex 为 BSD 许可），引导脚本在转码候选（.mp3/.opus，词典原生自带的照常直接播）
都落空后 fetch 原 .spx 交给解码器；二进制转字符串必须分块（`String.fromCharCode.apply`
参数个数有上限）；沿用 django-mdict 的经验修正——双声道时采样率减半，否则 NHK 的
32kHz 双声道 spx 播放过快。随之移除整套服务端转码：`spx_transcode.py`、`/dict-res` 的
按需转码钩子、`/admin/dictionaries/scan-spx` 与 `/transcode-spx` 端点、设置页的 ffmpeg
面板与 `spx_online_transcode` 开关、离线脚本 `scripts/transcode_spx.py`；ffmpeg 不再是
任何形式的依赖。`dict_entries` 的 `spx_pending_count`/`spx_scanned_at` 两列保留
（删列需要再一次 29GB 整表重建，不值得），但不再写入、不再对外暴露。已有的 mp3 全部
保留（其中约 10.5GB 是词典原生自带的真人发音，与新方案天然兼容；NHK 那 14 万个转码
产物现在是该批发音的唯一副本，删除 spx 的原文件已无法恢复，除非对该词典跑「重新解析」）。）；
版本：v1.52（**修复静默丢数据：同一部词典允许存在多条同名词条**。`dict_entries` 原有
`UNIQUE(dictionary_id, word)` 约束，导入时同名只留首条（`_batch_insert` 的 `seen_words`）。
设计意图是处理 StarDict `.syn` 别名冲突——那种情况两条内容完全一样，丢一条无所谓；但
**MDict 允许同一词头有多条内容不同的条目**（搜韵诗词全文检索版的「毛泽东」有 82 条，
是 82 首不同的诗词），实测 63 部词典里 49 部受影响，共静默丢失 **1,445,181 条**
（源 26,134,548 条 → 只入库 24,689,367 行），且不报错、也不体现在 word_count 里。
这是上游的原始设计（git blame：3ef05121 / 080442dc，2026-09-10），不是本分支引入的。
改动：① 迁移 `e5b7c9d1a3f4` 去掉唯一约束（SQLite 上是 autoindex、无法单独 DROP，
batch_alter_table 整表重建），并补 `(dictionary_id, word_lower)` 复合索引——查询按这两列
过滤，而原唯一索引建在 `(dictionary_id, word)` 上（word 非 word_lower），对查询本来就
使不上力；② 导入不再去重；③ 查询结果带条目 id（`schemas/query.py` 的 QueryResultItem
同步加字段）；④ **词条端点聚合渲染**：同一词典里匹配这个词（含变体）的全部条目合成
**一个** HTML 文档返回，条与条之间有小标题（序号/词头/注音）与分隔线——逐条各建 iframe
的话，搜韵展开一次要挂载 82 个沙箱文档；只传一条时输出与旧版逐字节一致；前端多条时
整组只用一个 iframe。前端把查询结果里那一组的条目 id 显式传给端点（`entry_ids`），
保证 iframe 里的条数与「共 N 条」一致——按 word 再推一遍变体集合可能对不上（查询用的
是用户输入推的变体，词头是词典自己的写法）。生词本**不受影响**：收藏按 `(user_id, word)`

整个重灌一遍——**词典 id 不变**（Token/用户白名单、生词本、检索范围勾选都不用重配；
词条 id 会变，但没有数据引用它）。刻意做全量重灌而不是只补缺失行：此前有几轮导入期改写
修复（资源引用改写、StyleSheet 展开），老行是老规则产出的，只补缺失会把新旧两种格式混在
同一部词典里；失败重跑即可，每次都从清空开始。源文件不在的词典跳过并计数。）；
版本：v1.51（去掉词条 iframe 里的滚动条：根因是词典用**负外边距做「出血」**——千篇汉语
词典是 `ul{margin:-12px -6px 0}`，左右各溢出 6px。这 6px 会引出**两根**滚动条：横向那根
占掉约 15px 视口高度，于是内容又纵向溢出，纵向那根跟着出现——所以「宽度和高度都有滚动条」
其实是同一个根因。修法是给注入的文档加 `html{overflow-x:clip}`：用 `clip` 而不是 `hidden`，
因为 `hidden` 会让 html 变成滚动容器（连带影响 position:sticky）。实测各词典在 760px 视口
下的横向溢出量：千篇恒为 6px，大辞泉/辞海/広辞苑/明镜/Weblio/大辭海全为 0，都是装饰性出血、
裁掉不丢内容。用 headless Chrome 做了 A/B 对照：去掉这行时横向滚动条出现（`clientHeight`
比 `innerHeight` 少 15px），加上后消失。）；

## 1. 总体架构

```
                        ┌───────────────────────┐
                        │        浏览器          │
                        │  Vue3 SPA（前台+后台）  │
                        └───────────┬───────────┘
                                    │ HTTPS
            ┌───────────────────────▼───────────────────────┐
            │        单一容器 mydict-app                       │
            │        FastAPI (Uvicorn, 单进程)                 │
            │  - 挂载 /       → StaticFiles 托管 Vue3 构建产物   │
            │                   （SPA 路由 fallback 到 index.html）│
            │  - 挂载 /api/*  → 后端接口                         │
            │  - Auth (用户/管理员 JWT)                          │
            │  - Token 鉴权中间件 + 限流（含匿名/开放使用判定）      │
            │  - 词典查询引擎（可插拔 Parser）                      │
            │  - 词典导入 / 后台管理 API                           │
            │  - 进程内内存缓存（热词/近期查询结果）                  │
            │  - 统计聚合（定时任务）                               │
            └───────┬─────────────────────────────┬──────────┘
                    │                              │
          ┌─────────▼─────────┐         ┌──────────▼──────────┐
          │  SQLite 数据库文件   │         │  文件存储 Volume       │
          │  （Volume 持久化）    │         │  词典原始文件           │
          └────────────────────┘         └──────────────────────┘
```

- **单容器部署**：前端 Vue3 构建产物与后端 FastAPI 打包进**同一个镜像**，由 FastAPI 通过 `StaticFiles` 直接托管，不再单独运行 Nginx/前端容器。第三方调用方与浏览器都访问同一个容器暴露的端口（如 `8000`），`/api/*` 走接口，其余路径回退到 SPA 的 `index.html`。
- 不引入独立数据库/缓存服务：数据库使用内置 **SQLite**（单文件，随容器挂载 Volume 持久化），缓存使用 **进程内内存缓存**（不引入 Redis）。整套服务只需 `docker run` 一个容器即可运行。

## 2. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Vue Router | 单一 SPA，`/admin/*` 路由做管理后台（需管理员角色），其余为用户前台 |
| 前端 UI 组件库 | Element Plus（后台）/ 自定义轻量组件（前台查询页，追求"标准词典 UI"观感） | 视觉规范见《UI设计规范.md》，Token 化实现见第 7 节 |
| 后端 | Python 3.12 + FastAPI + SQLAlchemy 2.0 + Pydantic v2 | 选 Python 主要因为词典解析（MDict/StarDict/ECDICT）开源库生态成熟 |
| 词典解析 | `readmdict`（MDict `.mdx`/`.mdd`）、自研 StarDict 解析（`.ifo/.idx/.dict[.dz]/.syn`，格式公开、字段简单）、ECDICT CSV 解析器（标准 csv 模块流式读取） | 统一实现 `DictionaryParser` 接口，便于后续扩展新格式 |
| 数据库 | **SQLite**（内置文件数据库，随容器 Volume 持久化），ORM 层使用 SQLAlchemy，保留未来切换 PostgreSQL 的可能性 | 已确认 |
| 缓存/限流 | **进程内内存缓存**（`cachetools` TTL Cache 或等价实现），承载：热门词查询结果缓存、Token/IP 限流计数器 | 已确认不引入 Redis；受限于单进程部署（Uvicorn 单 worker 或以 sticky 方式运行），如后续需要多进程/多副本部署需重新评估缓存方案 |
| 鉴权 | 管理员/用户：JWT（access + refresh）；第三方 API：静态 Token（Hash 存储，`Bearer <token>`） | |
| 任务调度 | APScheduler（进程内），用于统计聚合、限流计数器每日重置 | |
| 部署 | 单一 Docker 镜像（多阶段构建），FastAPI 用 `StaticFiles` 直接托管前端构建产物，无需 Nginx | |

> **单 worker 注意事项**：由于限流计数与热词缓存都存于进程内存，后端服务需以**单进程**方式运行（`uvicorn --workers 1`），否则多进程间状态不共享会导致限流失效、缓存命中率下降。当前使用频率不高，单进程可满足性能需求；如未来需要水平扩展，需将缓存/限流迁移至外部存储（如 Redis）。
>
> **SQLite 并发写**：单进程内仍有多线程并发访问 DB 的场景（FastAPI 同步路由跑在线程池、APScheduler 后台任务线程、大文件词典导入的批量 commit），SQLite 默认回滚日志模式下写操作互斥，并发写冲突会直接抛 `database is locked` 而不是等待。连接建立时统一开启 `PRAGMA journal_mode=WAL`（读不阻塞写）与 `PRAGMA busy_timeout=5000`（写冲突等待重试而非立即报错），见 [db.py](../backend/app/core/db.py)。

## 3. 数据库设计（SQLite / SQLAlchemy 模型，核心表）

```sql
-- 管理员（与普通用户分离，避免权限体系混淆）
admins (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  username      TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  created_at    TEXT DEFAULT (datetime('now')),
  last_login_at TEXT
)

-- 普通用户
users (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  username        TEXT UNIQUE NOT NULL,
  email           TEXT UNIQUE,
  password_hash   TEXT NOT NULL,
  status          TEXT CHECK (status IN ('active','disabled')) DEFAULT 'active',
  created_at      TEXT DEFAULT (datetime('now')),
  last_login_at   TEXT,
  allowed_dictionary_ids  JSON  -- 「可用词典」限制，NULL 为不限制，见 4.2.1
)

-- 词典
dictionaries (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  name          TEXT NOT NULL,
  format        TEXT CHECK (format IN ('mdict','stardict','ecdict')) NOT NULL,
  lang_from     TEXT NOT NULL,     -- 源语言：en / zh-Hans / zh-Hant / ja（早期数据可能是裸 zh，仍兼容）

  spx_pending_count INTEGER DEFAULT 0, -- 待转码的 .spx 发音数（同名同目录下没有非空 mp3/opus 产物的那些）；

  spx_scanned_at    TEXT,              -- 上次扫描发音资源的时间；NULL 表示从未扫过（升级前的存量词典）

  status        TEXT CHECK (status IN ('enabled','disabled')) DEFAULT 'disabled',

-- 词典解析后的词条索引（统一结构，便于跨格式、跨语言方向查询）
dict_entries (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  dictionary_id INTEGER REFERENCES dictionaries(id) ON DELETE CASCADE,
  word          TEXT NOT NULL,
  word_lower    TEXT NOT NULL,     -- 归一化用于检索（英文小写；中文保持原样）
  phonetic      TEXT,
  definition    TEXT NOT NULL,     -- 解析后的释义（HTML/纯文本，依来源格式而定；内含资源引用已在导入时改写为 /dict-res/... 绝对路径，见 5.5）
  extra         TEXT,              -- 格式特有的结构化元数据，JSON 字符串（如 ECDICT 的 tag/collins/oxford/exchange/frq）
  generation    INTEGER NOT NULL DEFAULT 0  -- 词条所属的「代」，等于 dictionaries.active_generation 才可见
)                                  -- 同一词典允许多条同名词条（MDict 允许），不设唯一约束
-- 索引：CREATE INDEX idx_dict_entries_word_lower ON dict_entries (word_lower);
--       CREATE INDEX ix_dict_entries_dict_word_lower ON dict_entries (dictionary_id, word_lower);
-- 查询时按 word_lower 精确匹配；前缀联想用 LIKE 'xxx%'（SQLite 对该模式可用索引），
-- 数据量增长后可评估引入 SQLite FTS5 全文索引做联想/模糊搜索。

-- 「代」与重新解析：所有读 dict_entries 的查询都 JOIN dictionaries 并要求
-- generation = active_generation（app/services/entry_scope.py 统一封装）。重新解析时：
--   1. 新词条写成 active_generation + 1，每批提交——对查询不可见，旧词条照常可查；
--   2. UPDATE dictionaries SET active_generation = 新代——一行更新即完成切换，原子、瞬时；
--   3. 分批删除旧一代（已不可见）。中途失败只需清掉写了一半的新一代，旧词条不受影响。
-- 不「先删后灌」：那会让词典在整个解析期间查不到内容，且大事务长时间独占 SQLite 写锁，
-- 站内每次查询都要写的 query_log 会因 busy_timeout 超时而报错。也不用暂存表再拷贝：
-- 实测 100 万条（约 2GB）多一轮拷贝要多花约 17% 的时间，且峰值占用 3 倍词典体积
-- （SQLite 删除后不缩文件）；「代」方案只多占 1 倍，与直接写入等价。
```

> **导入时解析入库**：`dict_entries` 采用"导入时统一解析为标准结构存库"的方案，而非运行时动态解析原始词典文件，优点是查询性能可控、便于跨词典/跨语言方向聚合排序；代价是导入耗时更长、存储占用更大（原始文件 + 结构化数据）。当前数据规模不大（用户确认无需 Redis/高并发），该方案足够，且实现简单、便于统计和联想查询。

> **生词本释义快照**：`vocab_items`/`token_vocab_items` 的 `phonetic`/`definition` 是**收藏那一刻**从 `dict_entries` 复制的快照，而非每次展示时实时关联查询。这样即使后续该词典被禁用、删除或重新导入覆盖，生词本里已收藏的词依然能正常显示原有释义，不会因为词典状态变化而"变空"；代价是词典更新后，已收藏词条的释义不会自动跟着刷新（如需要可作为后续「重新同步释义」的可选操作）。

> **时间与时区约定**：所有时间戳（`created_at`/`imported_at`/`last_login_at` 等）一律以 **UTC** 存储，且是 naive 值（SQLite / SQLAlchemy 的 `DateTime` 不带时区）。但业务上的「一天」按**部署本地时区**划分——管理员看的是本地日历日，统计页的日期选择器给的也是本地日期。两者口径不同，因此任何「按天」的过滤都不能写成 `func.date(created_at) == 本地日期`：在 UTC+8 部署下，本地 00:00 到 UTC 偏移之间会整整错开一天，表现为「今日查询量」等统计每天凌晨 8 小时恒为 0。正确做法是用 `core/timeutil.py` 把本地日换算成对应的 UTC **半开区间** `[当日 00:00 本地, 次日 00:00 本地)`，再做 `>= 起 AND < 止` 比较；这样写顺带能让 `ix_query_logs_created_at` 索引生效（`func.date(col)` 会让索引失效）。注意 `timeutil` 返回的边界是 **naive UTC**——SQLAlchemy 在 SQLite 上会丢掉 bind 参数的 tzinfo，传 aware 值反而会把偏移量算错。部署时区由 `TIMEZONE` 环境变量决定，留空或配置了无效值（会记 warning）则回落到容器/宿主机系统时区；系统时区只是当前时刻的固定偏移、不含夏令时规则，有夏令时的地区请显式配置 `TIMEZONE`（如 `America/New_York`）。

## 4. API 设计

### 4.1 对外查询与收藏 API（第三方，Token 鉴权）

| Method | Path | 说明 |
|---|---|---|
| GET | `/api/v1/query?word=xxx&dict=id1,id2&from=en&to=zh-Hans&full_style=false` | 查询单词，三种匹配方式按优先级取第一个生效：① `dict` 显式指定词典 id；② `from`（可选配 `to`）显式指定语言方向，精确匹配 `lang_from`（`from=zh` 时兼容匹配 `zh`/`zh-Hans`/`zh-Hant`）；③ 都不传则按输入文字自动识别语言（英文输入优先英汉词典，中文输入优先汉英词典；语言识别只做粗粒度的"含 CJK 表意文字→中文，否则→英文"，不识别日文假名，为 `ja` 等值的词典不参与这一档自动识别，需要用 `from=ja` 显式指定）。以上任一方式选出的词典集合，最终都要与 Token 的「可用词典」设置（见下）取交集，Token 无法通过 `dict`/`from` 绕过限制查到限制外的词典；`full_style`（可选，默认 `false`）为 `false` 时返回结果里的 `definition` 会被去除 HTML 标签转为纯文本，为 `true` 时保留原始 HTML（含内联样式、图片等） |
| GET | `/api/v1/suggest?prefix=xxx&limit=10&dict=id1,id2` | 前缀联想（选做），同样受 Token「可用词典」限制 |
| GET | `/api/v1/dictionaries` | 获取当前可查询的词典列表（id、name、lang_from、lang_to），已按 Token「可用词典」设置过滤 |
| GET | `/api/v1/vocab` | 查看当前 Token 的收藏列表（分页/搜索），每条返回 `word/phonetic/definition/note/dictionary_id/created_at`，`definition` 为收藏时的释义快照，直接展示无需再次查词典 |
| POST | `/api/v1/vocab` | 收藏单词到当前 Token 的生词本（`{word, dictionary_id?, note?}`）；服务端按 `dictionary_id`（或未指定时取匹配到的首个已启用词典）从 `dict_entries` 查出当前释义，连同 `phonetic` 一并写入快照，客户端无需也不能自行传入释义内容 |
| DELETE | `/api/v1/vocab/{id}` | 删除一条收藏 |

请求头：`Authorization: Bearer <token>`（可缺省，见下）
鉴权规则：
- 查询类接口（`query`/`suggest`/`dictionaries`）：
  - 携带有效 Token → 正常鉴权，按 Token 每日限流计数。
  - 未携带 Token：若系统设置 `open_access=true`，按匿名请求放行，以调用方 IP 计入 `anonymous_ip_rate_limit_per_min` 限流，`query_logs` 中 `token_id` 记为空、`status` 标记来源为匿名；若 `open_access=false`，返回 `401`。
- 收藏类接口（`/api/v1/vocab/*`）：**始终要求携带有效 Token**，不受 `open_access` 影响（无身份则无法归属收藏数据），未携带或 Token 无效一律 `401`。
- Token 被禁用 → `403`；超出限流 → `429`（返回 `Retry-After`）。
错误码：查询未命中返回 `200` + `results: []`（而非 404）。

#### 4.2.1「可用词典」设置

Token（第三方 API 调用方）与登录用户都可以配置自己的「可用词典」，限定查询范围只在指定的几部词典内进行：

- **存储**：`api_tokens.allowed_dictionary_ids` / `users.allowed_dictionary_ids`，均为可空的 JSON 数组列（SQLAlchemy 原生 `JSON` 类型，ORM 层自动序列化，不是 `detail`/`extra` 那种手动 `json.dumps` 的 TEXT 列——这里就是单纯的 id 列表，没有自由结构需要透传）。`NULL`/`None` 表示不限制（默认），可查询全部已启用词典；非空数组时按数组内容与已启用词典取交集。设置为空数组等价于不限制——"限制到零个词典"不是有意义的可用状态。
- **生效范围**：`query_service.resolve_dictionaries()` 在按 `dict_ids`/`from`+`to`/自动识别语言 任一方式选出候选词典之后，统一再与「可用词典」取一次交集，调用方无法通过显式参数绕过限制；`/api/v1/dictionaries`、`GET /api/auth/me` 里的 `allowed_dictionary_ids` 字段供调用方自查当前配置。
- **谁来配置**：
  - Token：由管理员在后台「Token 管理」逐个配置（`PUT /api/admin/tokens/{id}/allowed-dictionaries`），因为 Token 是管理员为第三方创建/管理的。
  - 用户：自助配置，前台首页顶栏用户名下拉菜单「词典选择」，弹窗展示全部已启用词典勾选（`GET /api/dict/dictionaries`，不受当前限制过滤，否则限制过一次就没法再选回来），保存调用 `PUT /api/auth/allowed-dictionaries`。
- **清理**：设置时会把已不存在（如词典被删除）的 id 过滤掉再存库，避免限制列表堆积失效条目。

#### 4.2.2 查询历史 / 生词本按语言分类

- **查询历史**：直接复用 `query_logs`（已有的原始查询明细表，见 3 节），不额外建表——`GET /api/dict/history` 按 `user_id` 过滤、只取 `status='success'` 的记录（未命中没有 `dictionary_id`，历史里也没法直接收藏，意义不大）取最近 100 条。`query_logs` 定位仍是"近期明细，定期归档/清理"，历史功能因此也只保证"最近"，不承诺永久可查——这点在功能设计上是可接受的（用户真正想留存的词应该收藏到生词本，历史只是辅助入口）。
- **生词本按语言分类**：`vocab_items.dictionary_id` 关联到词典的 `lang_from`，`GET /api/vocab/languages` 返回当前用户生词本里出现过的去重语言列表，前台生词本页左上角按此渲染 tab（无圆角、下划线高亮，复用 NavBar 导航 tab 同款视觉）；`GET /api/vocab?lang_from=xxx` 按语言过滤列表，服务端过滤保证分页游标始终正确（不是前端拿到一页数据后再筛，那样翻页会错）。
- **前端复用**：查询结果面板（`components/EntryPanel.vue`）与历史记录列表共用同一个收藏图标组件（`components/FavoriteButton.vue`），收藏/取消收藏的状态与请求逻辑也抽成组合式函数 `composables/useFavorites.ts`，避免首页查询页和历史页各自维护一份同样容易出 bug 的收藏态逻辑。

#### 4.2.3 语言路由与查询扩展

查询时怎么决定「去哪几部词典里找」，按以下优先级（`query_service.resolve_candidates()`）：

1. 显式 `dict=a,b,c` —— 调用方说了算，且仍与「可用词典」取交集
2. 显式 `from`/`to` —— 全部候选都算「优先」，不做兜底
3. 按输入文字的字符脚本自动识别 —— 「优先语言」= `lang_from` 与输入语言一致的那批

第 3 种情况用的是**软过滤**而不是硬过滤：先用优先语言的词典查，**有结果就只返回这些**（避免一次查询把中/日/英各语言的词典全铺出来）；一部都没命中，才退到其余语言的词典，并在结果项上标记 `lang_match=false`，前台据此显示「其他语言词典」徽标。

之所以必须做兜底：`lang_from` 是导入时按采样自动识别的，**并不可靠**。实测用户的 63 部词典里有 6 部中文词典被判成 `en`，按硬过滤的话这 583,823 条内容（含「汉典」462,817 条）永远查不到。采样逻辑已改为跨整部词典取词头 + 剔掉无信息量样本，但**已入库的值不会自动更新**——需要跑 `python -m app.cli redetect-languages` 回溯修正（见 8.6）。

缓存 key（`core/query_cache.py`）用**完整候选集**而不是优先语言那批：只按优先语言做 key 的话，「优先语言没命中」这个空结果会被缓存住，兜底路径就永远走不到了。

**查询扩展**（`services/query_expand.py`）：把查询词展开成一组等价写法后再查——繁简（OpenCC 的 `t2s`/`s2t`/`s2tw`/`s2hk` 四个配置，转换是「一对多」的所以多挂几个）、全角/半角（NFKC 归一，另加 ASCII→全角 的反向变体）。SQL 由等值匹配改为 `word_lower IN (变体…)`，`word_lower` 上的 B-tree 索引直接服务 `IN`，无需改表结构。扩展规则版本号（`EXPANSION_VERSION`）要进缓存 key，否则改规则后新结果会被旧缓存挡住。只做「同一条词条的不同写法」，**不做模糊匹配**；实测对用户 5 部繁体词典抽样 1075 个简繁不同形的词头，91.4% 能被简体输入覆盖到，剩余是「一个字对应多个繁体字」的歧义情形（屍/尸、剋/克、乾/干）。

## 5. 词典解析原理与可插拔架构

### 5.1 统一接口

```
DictionaryParser (interface)
 ├─ parse(file_paths) -> Iterator[Entry(word, phonetic, definition, extra)]
 ├─ sample(file_paths, limit) -> list[Entry]        # 顺序采样，供判定释义用什么文字写
 ├─ sample_headwords(file_paths, limit) -> list[str] # 跨整部词典均匀取词头，判定 lang_from
 ├─ MDictParser        # 解析 .mdx / .mdd
 ├─ StarDictParser     # 解析 .ifo/.idx/.dict(.dz)/.syn
 └─ EcdictParser       # 解析 ECDICT 的 ecdict.csv
```

导入流程：获取源文件（见 5.1.1 两种方式） → 校验文件完整性/格式 → 对应 Parser **流式**解析（逐条 yield，不整份读进内存）→ 批量写入 `dict_entries`（分批 commit，如每 2000 条一批，避免大文件内存溢出/长事务锁库）→ 更新 `dictionaries.word_count/status` → 清空查询缓存 → 记录审计日志。三种格式的原始文件结构与解析步骤如下。

**语言方向的自动识别**（`services/language_detect.py`）：词典自身的元数据没有可靠的语言字段（`StarDict` 的 `.ifo` 与 MDict 的 header 都没有），所以改为采样后按字符脚本判断。两个采样接口都与 `parse()` 的关键差别是**只读且有读取量上界**、绝不写盘——尤其**刻意不加载 `.mdd`**：`parse()` 会把其中的图片/音频全量落盘，采样不该有这个副作用。

- `sample_headwords()` 判定 `lang_from`（词头用什么文字写）。它必须**跨整部词典**均匀取，不能只取开头：词典开头常常是索引项、数字条目或拼音索引（实测「汉典」前几条是 `0`/`110`/`120`，「古漢語常用字」是 `a1`/`a2`/`a3`），只看开头会把整部中文词典判成 `en`，而 `lang_from` 是查询路由的依据，判错等于那部词典的内容永远查不到。能做到「取中段」的前提是**不必顺序读完整个词条流**：`mdict-utils` 在 `MDX.__init__` 里就把整个词头表读进内存了（`_key_list`，元素是 `(record_offset, utf-8 字节)`），按下标取值是纯内存操作；StarDict 按字节偏移 seek 到 `.idx` 的记录边界（`.idx.gz` 不能随机 seek，整份解压后步进，受 32MB 上限保护）；ECDICT 按行偏移 seek 后取下一整行。取样还会剔掉纯数字/符号的词头（索引项既不贡献拉丁也不贡献汉字，留着只稀释样本），并且**跑完整段再统一下采样**——中途「收满 limit 就停」会退回「只取开头」。
- `sample()` 判定 `lang_to`（释义用什么文字写）。释义只能顺序多读一些再过滤，且是**读到够 limit 条「有信息量」的词条才停**（外加扫描条数上限）：扫描版词典整条释义就是一个 `<img>`，纯图片词条判不出语言；纯数字词头的条目同理。过滤用 `is_informative()`——词头要有有意义的文字字符，且剥掉标签与字符实体后正文不少于 2 个字符（阈值取 2 而不是更大：真实词典里 `n. 苹果` 这种极短释义是合法内容，不能误伤）。

**字符实体必须先剥掉**（`strip_markup()`）：`&nbsp;` 会被当成 4 个拉丁字母算进占比，而 MDict 释义里排版实体很密集（每行缩进都是若干个），足以把中文释义的拉丁占比拉过汉字、判成 `en`。

判定规则：先看有无假名（平假名/片假名是中英文都不会出现的排他性判据，但要求数量至少为汉字的三分之一，避免中文词典在词源里夹几个假名就被误判成日文），否则比较汉字与拉丁字母的占比——**词头侧决定 `lang_from`、释义侧决定 `lang_to`**，于是英汉（`en → zh-Hans`）、汉英（`zh-Hans → en`）、汉语单语（`zh-Hans → zh-Hans`）、英英（`en → en`）四种常见情形都能区分；简繁则统计样本中「繁体独有字形」的占比（简体文本里传统字形是零出现，占比 ≥1% 即判 `zh-Hant`）。因为两侧的取样方式不同（词头跨全词典、释义只能顺序取），`detect_language()` 接收的是**两个独立的列表**而不是一批 `ParsedEntry`——判定只看各自的字符构成，不需要配对。**能力边界**：同用拉丁字母的语言之间区分不了（法语/德语/西班牙语→中文都会判成 `en`）；扫描版词典整页是图片、没有任何可提取文字，任何采样方式都判不出（实测「新华多功能字典」属于这类，只能手工设置语言方向）；有效字符少于 20 个时该侧返回 `None`；这几种情况下 `dictionary_service` 都回落到 `en`/`zh-Hans`（`dictionaries.lang_from/lang_to` 是 NOT NULL，必须落到具体值）。识别在后台导入线程里执行，不拖慢接口返回；采样失败只写一条警告日志，不让整次导入失败。

**已入库的错值需要单独回溯**：采样逻辑改好之后，既有词典的 `lang_from` **不会自动更新**。所以提供 `python -m app.cli redetect-languages`（见 8.6）按新逻辑重新识别并写回，只覆盖识别出结论的那一侧。这不能省：查询路由依赖 `lang_from`，而 4.2.3 的软过滤只在「优先语言一部都没命中」时才兜底——查一个简体词典里也有的词时，误判成 `en` 的词典仍然不会出现。

#### 5.1.1 两种导入入口：浏览器上传 / 从服务器目录导入

考虑到部分 MDict 词典文件体积可达 GB 级，纯浏览器 `multipart` 上传在公网/弱网环境下容易超时或过慢，「词典管理 → 导入」提供两种互补的方式：

1. **浏览器上传**（适合中小文件、操作最简单）：
   - `POST /api/admin/dictionaries`，`multipart/form-data` 直传文件 + `format`/`lang_from`/`lang_to` 等元信息，服务端存到临时目录后解析。
2. **从服务器目录导入**（推荐用于 GB 级大文件）：
   - 容器统一用 `/data` 作为用户数据根目录，其下 `/data/dicts` 专门用于存放**待导入**的词典源文件：管理员运维时用 `docker cp`/`scp`/挂载宿主机目录等方式，把词典文件预先放进 `/data/dicts`，全程不经过 HTTP 上传。
   - `GET /api/admin/dictionaries/dicts-dir-files?path=<相对路径>&recursive=<bool>`：列出 `path` 指向的目录下的条目（`path` 省略或空串即根目录 `/data/dicts` 本身），返回 `{path, entries, dictionaries, skipped}`。`entries` 是原始的目录条目列表（文件名/大小/修改时间/`is_dir`/`imported`），供前端逐级浏览子目录；`dictionaries` 是把文件按 `(格式, 主干)` 归组出的待导入词典单元，管理员不再需要自己判断哪几个文件属于同一部词典：
     - 后缀决定格式（`.mdx`/`.mdd`→mdict，`.ifo`/`.idx`/`.dict`/`.syn`/`.dict.dz`/`.idx.gz`→stardict，`.csv`→ecdict），双后缀优先匹配（否则 `x.dict.dz` 会被截成不存在的 `.dz`），大小写不敏感；分组键带格式前缀，因此同一目录下的 `foo.mdx` 与 `foo.ifo` 是两部不同格式的词典，不会因为主干相同被并成一部。
     - **多卷资源并卷**：MDict 超过单文件上限时会拆成 `X.mdd` / `X.1.mdd` / …（实测最多到 `.6`），这些卷会并入同目录下 `X.mdx` 那一组。但仅在能对上某个 `.mdx` 主干时才剥卷号——`X.1` 也可能是词典名本身（如「三省堂スーパー大辞林3.0」），无条件剥离会把单词典拆成多个「缺少 .mdx」的假分组且漏掉资源；对不上主干的孤立 `.mdd` 仍单独成组并标缺件。
     - `recursive=true` 时**逐层递归扫描**整个子树（深度上限 4，跳过 `.` 开头的目录），每个目录各自归组——同一部词典的配套文件总在同一文件夹里，混在一起反而会让不同目录下的同名文件互相干扰。每个分组带 `dir`（相对 `/data/dicts` 的所在目录）供前端区分。这样「一个文件夹一部词典」的整理方式（很常见）可以一次全列出来批量导入，不必逐层点进去。
     - 名称按「一个文件夹只有一部可导入词典时用目录名，否则用文件名主干」给出：目录名通常比文件名主干可读得多（如「[英] 韦氏大学词典」vs「[英-英]语音版图文版Merriam-WebstersCollegiateDictionary」）；但扫描起点是容器而不是某部词典的文件夹，一个目录放多部词典时目录名也无法区分它们。StarDict 优先取其 `.ifo` 的 `bookname`。名称在前端可改。
     - 每部另含 `files`（每项含相对 `/data/dicts` 的 `relpath`，导入时直接回传）、`total_size`、`importable` 与 `reason`（缺哪些必需文件，如 mdict 缺 `.mdx`、stardict 缺 `.idx`/`.dict`；残缺分组照常列出并标红，让人看得见而不是被悄悄忽略）、`imported`（组内文件是否**都**已被某个 `dicts_dir` 词典消费过，按相对 `/data/dicts` 的完整路径比对，同名文件放在不同子目录下不会互相误标；已导入的组默认不勾选，仍可手动勾上重新导入成另一部词典）；`skipped` 是被忽略的无关文件（相对 `/data/dicts` 的路径，递归时可达上百个，前端只显示数量并用悬浮层列出）。
     - `path` 校验拒绝 `..`/绝对路径等越权访问。
   - `POST /api/admin/dictionaries/import-from-dicts-dir`：请求体只传路径与元信息，如 `{"format":"mdict","name":"牛津高阶","files":["cn/oxford.mdx","cn/oxford.mdd"]}`（`files` 支持 `子目录/文件名` 形式的相对路径，无需传输文件内容），服务端按相对路径在 `/data/dicts` 内定位，同样拒绝路径穿越；`lang_from`/`lang_to` 可省略，省略时由服务端自动识别（见 5.1），识别结果随任务 `result` 一起返回。
   - **可选的省空间开关** `skip_resources`（默认 false）：为 true 时只导入释义，不解包 `.mdd` 里的图片/发音。MDict 的词条资源常单独占几个 GB（实测某词典库 `.mdx` 合计 3.9GB、`.mdd` 合计 31GB），解包一份等于再占一份磁盘，勾上后磁盘占用能降一个数量级，代价是查词时没有发音与插图。实现上给 `DictionaryParser.parse()` 的 `resource_dir` 传 `None`，此时连 `res/` 目录都不创建，也不改写释义里的资源引用（改了只会指向不存在的文件，保留原始相对引用更诚实）。
   - **批量导入**由前端逐部串行调用上面这个单部接口实现（任一时刻只跑一部），不新增后端批量端点：并发导入会争抢 SQLite 的写锁、并叠加多份大词典解析的内存/磁盘压力；串行还让每一部都有独立的 `task_id`，某一部失败不影响其余，界面按行显示各自的成功/失败与识别出的语言方向。中途关闭页面时在途那一部照常跑完（后台 daemon 线程），未开始的只是不再被调度——重新打开后扫描会把已完成的组标成 `imported`（默认不再勾选），批量可续跑且幂等。

两个入口的解析入库都是异步的（见 5.1.2），响应体不再是完整的词典对象，而是 `{"task_id": <int>}`；调用方轮询 `GET /api/admin/tasks/{task_id}` 获知真正的导入结果。

#### 5.1.2 导入异步化：避免大词典解析耗时超过前端请求超时

早期实现里，`POST /api/admin/dictionaries` 与 `POST /api/admin/dictionaries/import-from-dicts-dir` 都是解析、批量入库全部跑完才返回响应——大词典（几十万词条）解析耗时可能到几分钟，而前端 axios 全局请求超时是 10 秒（`frontend/src/api/request.ts`），超时后客户端直接中断等待、`submitImport` 里的 `importing` 状态随之结束，但后端线程池里的导入任务并未被取消，还在继续跑，最终会成功提交；管理员看到的现象就是"点了开始导入，转了一下圈就没反应了，词典却过一阵子才能查到"。

现在的流程：
1. 请求线程内先做格式（`format` 是否受支持）与文件名后缀（是否匹配声明的 `format`）校验，这两项很快，坏输入照常同步 4xx 返回。
2. 校验通过后，`dictionary_service.start_dictionary_import()` 在 `background_task_service` 登记一个任务并 `threading.Thread` 派发真正的解析/批量入库（`import_dictionary()`），派发的线程用独立的 `SessionLocal()` 会话（不能沿用请求 session，请求已经结束）；路由立即返回 `{"task_id": task.id}`。
3. 前端拿到 `task_id` 后轮询 `GET /api/admin/tasks/{task_id}`，`status` 为 `running` 时继续轮询；变成 `success` 时用 `result` 里的 `{word_count, lang_from, lang_to}` 提示成功、刷新词典列表（目录批量导入时逐行显示这一部识别出的语言方向，便于管理员核对）；变成 `error` 时用 `error` 文本提示失败原因（含解析器校验出的 `ValueError`，如"缺少必要文件"）。

`background_task_service.py` 相应从"任务结束立即从登记表移除"改为保留终态（`success`/`error`）10 分钟供轮询方读取，超时未取才清理；`GET /api/admin/tasks/running`（管理后台顶栏跨标签页展示"正在导入"）只返回 `status=running` 的任务，语义不变。
   - **路径安全**：文件名做白名单校验（禁止包含 `/`、`\`、`..`），只允许引用 `/data/dicts` 目录下**已存在**的文件，不接受任意绝对路径，避免路径穿越读取容器内其他文件。
   - **单文件格式限制**：ECDICT 一个 CSV 就是一部完整词典（`EcdictParser` 只读 `file_paths[0]`），浏览器上传与从目录导入两条路径都会校验 `format=ecdict` 时只能选 1 个文件，多选直接 422 拒绝，避免选中多个 CSV 时后面的文件被静默丢弃、只导入了第一个（真实出现过的问题）；MDict/StarDict 本身需要多个配套文件，不受此限制。
   - 解析成功后源文件**留在原处**，不移动、不复制、不归档——`/data/dicts` 是用户自己管理的目录（`docker cp` 放进去的），导入只读取不接管，后续要不要清理由用户自己决定；`dictionaries.import_method` 记为 `dicts_dir`，删除词典时也不会碰这些文件（见 5.5 第 6 点）。这与"浏览器上传"路径不同：那条路径的源文件本就是本应用暂存的临时文件，会被移动归档到 `source/` 并在删除词典时一并清理。

### 5.2 MDict（`.mdx` / `.mdd`）

MDict 是二进制封装格式，社区已逆向出完整规格（参考实现如 `readmdict.py`、`writemdict`），本项目直接复用成熟的开源解析库，不自行逆向：

1. **文件头**：开头是一段 XML 元信息（标题、简介、`Encrypted` 加密标记、`Encoding`、`GeneratedByEngineVersion`），据此判断文本编码（UTF-8/GBK）与是否加密。
2. **关键字索引块（Key Block）**：其后是若干个经 `zlib`/`lzo` 压缩的数据块，每块内部是排序好的 `(单词文本, 记录偏移量)` 列表；块的数量、压缩前后大小、Adler32 校验和记录在紧邻的 Key Block Info 区。部分 mdx 对索引区做了额外的简单加密（`Encrypted=2`），需要用规格中公开的算法（基于文件头信息派生的密钥）先解密再解压。
3. **释义记录块（Record Block）**：结构与 Key Block 类似，是压缩后的记录内容流；每个词条的偏移量指向解压后记录流中的某个位置，取该位置到下一词条偏移量之间的内容即为该词的 HTML 释义原文。
4. **导入策略**：调用解析库顺序遍历 `(word, html)` 键值对，`word` 写入 `dict_entries.word`，`html` 原文写入 `definition`（前台渲染时按 HTML 展示，保留原词典的排版/样式）。
5. **`.mdd` 资源文件**：结构同 `.mdx`，但键是资源路径（如 `\pic\apple.png`），值是二进制文件内容（图片/音频/CSS）。这是 `.mdx` 释义 HTML 里 `<img>`/发音等资源的来源，纳入 MVP 首期实现，具体存储与转发方案见 5.5。
6. **LZO 压缩块（实现限制）**：解析库 `mdict-utils` 只有在额外装了可选的 `python-lzo` 时才支持 LZO 压缩块，否则对引擎版本 <2.0 的老词典直接抛 `RuntimeError("LZO compression is not supported")`。`python-lzo` 与它依赖的 `liblzo2` 都是 GPL，与本项目 MIT 授权不兼容，因此镜像里不装。`MDictParser` 把这一种 `RuntimeError` 转成 `ValueError`（走既有的解析校验错误通道），管理员看到的是「该词典使用了 LZO 压缩（MDict 引擎版本低于 2.0），当前构建未启用 LZO 支持」，而不是笼统的「服务器内部错误」。这类词典改用**离线转换**：`scripts/mdict_lzo_to_ecdict.py` 把 `.mdx` 导出成 ECDICT CSV，再走 ECDICT 通道导入（该脚本是运维工具、不属于运行时代码，只有运行它才需要 python-lzo；只导出词条正文，`.mdd` 里的图片/发音不带）。
7. **多卷资源**：`.mdd` 超过单文件上限时会拆成 `X.mdd`/`X.1.mdd`/…，扫描归组时会并入 `X.mdx` 那一组（见 5.1.1），不会因为主干不同被拆成多部词典。
8. **`StyleSheet` 样式标记**：文件头的 `StyleSheet` 字段定义了一批「编号 →（开始标签, 结束标记）」的替换规则，每个编号占三行（编号 / 开始 / 结束），正文里写 `` `编号` `` 引用它——例如 `` `1` `` 可能是 `<b><center><font size=5 color=Green>`、`</font></center></b><hr>`（词头居中加粗加分隔线），`` `2` `` 是 `<br>`、`` `10` `` 是品红色字体。这是 MDict 客户端才会展开的东西，**不展开的话标记就原样显示出来，看起来就是排版错乱**（实测多功能汉语辞典和高级成语词典全部 101653 条中招）。展开规则见 5.5 第 3 点的改写表；实现在 `app/parsers/mdict_stylesheet.py`。

### 5.3 StarDict（`.ifo` / `.idx` / `.dict[.dz]` / `.syn`）

StarDict 是完全公开、无加密的文本+二进制组合格式，官方有详细格式手册，可自行实现轻量解析器（不依赖第三方库）：

1. **`.ifo`**：纯文本 `key=value`（类似 INI），包含 `wordcount`（词条数）、`idxfilesize`、`sametypesequence`（该词典释义的默认数据类型，如 `m`=纯文本、`h`=HTML、`x`=XDXF）等元信息，先解析出来确定后续按什么格式解释 `.dict` 内容。
2. **`.idx`**：一条条定长/变长记录顺序排列：`单词字符串`（以 `\0` 结尾）+ `4 字节大端整数偏移量`（部分词典是 8 字节，取决于 `.ifo` 的 `idxoffsetbits`）+ `4 字节大端整数长度`。按顺序整体读一遍即可拿到全部 `(word, offset, length)` 三元组，无需理解排序规则（本项目导入后统一在 `dict_entries` 里建索引，不依赖 StarDict 自身的排序做二分查找）。
3. **`.dict` / `.dict.dz`**：原始释义内容仓库，按 `.idx` 给出的 `offset`/`length` 去读取对应字节片段即为该词的释义原文；若为 `.dict.dz`（dictzip 压缩，一种支持随机访问的 gzip 变体），导入阶段可直接完整解压一次成临时文件再按偏移读取，简化实现（无需实现 dictzip 的分块随机访问）。
4. **`.syn`（可选）**：同义词/别名表，结构类似 `.idx`，把一个别名字符串映射到 `.idx` 中的词条序号。导入时可将别名也作为独立的 `dict_entries` 记录写入（`definition` 指向/复制主词条内容），让用户查别名也能查到结果。
5. 解析出的原始内容按 `sametypesequence` 指示的类型（`m`/`h`/`x`）做相应处理：纯文本直接存，HTML 直接存，XDXF（一种 XML 词典标记）转换为可展示的 HTML 或纯文本摘要。

### 5.4 ECDICT（`ecdict.csv`）

ECDICT 是最简单的一种——一个带表头的 CSV 文本文件，用标准库 `csv.DictReader` 流式逐行读取即可，无需任何专用解析库：

1. **字段**：`word, phonetic, definition, translation, pos, collins, oxford, tag, bnc, frq, exchange, detail, audio`。其中 `definition` 为英文释义、`translation` 为中文释义（均可能是多行，按词性分段，如 `n. xxx\nv. xxx`），`tag` 是考纲标签（如 `zk`中考 `gk`高考 `cet4`/`cet6`/`ky`考研/`toefl`/`ielts` 等空格分隔），`exchange` 是词形变化（如 `p:did/d:done/i:doing/3:does`，前缀字母表示时态/单复数/比较级类型），`collins`/`oxford`/`bnc`/`frq` 是词典星级与词频排名。
2. **导入映射**：`word`→`word`，`phonetic`→`phonetic`，`definition` + `translation` 组合成展示用的 `definition`（中英对照展示）；`pos`/`collins`/`oxford`/`tag`/`bnc`/`frq`/`exchange` 序列化为 JSON 存入前面新增的 `dict_entries.extra` 字段，供前端展示"牛津3000""四级""比较级 harder"等标签徽标，是比 MDict/StarDict 更丰富的结构化数据来源。
3. **批量写入**：ECDICT 完整版词条量较大（数十万到百万级），用 `csv.DictReader` 按行迭代 + 每 2000 行 `executemany` 批量插入，避免一次性读入内存或逐行单独 commit。
4. **汉英（zh→en）方向的支持方式**：ECDICT 本身是英→汉词典，不直接提供"输入中文查英文"的反查索引。两种可选方案：
   - **方案 A（推荐）**：直接导入一部现成的汉英方向词典（MDict/StarDict 格式的汉英词典），作为独立的 `dictionaries` 记录（`lang_from=zh, lang_to=en`），与 ECDICT 并存，查询时按输入语言自动路由。
   - **方案 B（增强，可选）**：导入 ECDICT 时额外构建一份"反查索引"——解析 `translation` 字段中的中文词/短语（按行、按顿号/逗号切分），把每个中文词条也作为一条 `dict_entries` 记录写入（`word`=中文词，`definition`=指回英文词头及其释义），使得中文输入也能查到该英文词。此方案依赖对 `translation` 文本做简单分词/切词，可能存在噪音（如释义中夹杂的中文虚词被误当作独立词条），首期建议作为可选增强，优先用方案 A 保证质量。
5. **`detail` 列透传到 `extra`（汉语词典场景需要）**：标准 ECDICT 语料本身不使用 `detail` 列存实质内容，但本项目导入的其他中文语料（见 5.4.1）需要携带比 `collins/oxford/tag/bnc/frq/exchange` 更丰富的结构化信息（拼音、部首、笔画、字形结构、同/反义字、成语出处等）。`EcdictParser` 因此约定：若某行 `detail` 列非空且是合法 JSON，解析后与 `pos`/`collins`/`oxford`/`tag`/`bnc`/`frq`/`exchange` 一并合并进 `dict_entries.extra`（`detail` JSON 中的 key 覆盖同名默认字段），非 JSON 或空值则按原 ECDICT 语义忽略。

#### 5.4.1 汉语词典数据源：chinese-dictionary 转换方案

评估了开源语料 [mapull/chinese-dictionary](https://github.com/mapull/chinese-dictionary)（MIT License）作为"汉语词典"（`lang_from=zh, lang_to=zh`）的数据来源，用于覆盖 Q17 明确的第三种词典类别。该项目本身是纯中文语料（字/词/成语，JSON 格式），与 ECDICT 面向英文词条的字段设计不匹配，**不做"格式转 ECDICT"的语义包装，只复用其 CSV 解析管线**：

1. **源数据特点**：
   - `character/char_base.json`、`character/char_detail.json`（及 `common/` 子集）实际是"每行一个 JSON 对象、行尾带逗号、整体不带 `[...]` 包裹"的类 NDJSON 格式，需按行读取、去掉行尾逗号后再 `json.loads`；`idiom/idiom.json`、`word/word.json`、`character/polyphone.json`、`character/related.json` 则是标准 JSON 数组，可直接 `json.load`。
   - `word.json`（32万余条，含成语）与 `idiom.json`（5万余条，字段更丰富：出处/引用/故事/近反义/易错写法）中的同一成语，前者释义信息较简略，转换时以 `word.json` 为主、按 `word` 精确匹配用 `idiom.json` 的字段做增强，避免两份数据都导入同一词典造成 `UNIQUE(dictionary_id, word)` 冲突。
2. **离线转换脚本**（不进入运行时代码，放在仓库 `scripts/chinese_dictionary_to_ecdict.py`，一次性运行产出 CSV 后即可归档）：产出两份 ECDICT 风格 CSV，经标准导入流程（浏览器上传或 `/data/dicts` 目录导入）各自作为独立 `dictionary` 记录：
   - **汉语字典**（源：`character/char_detail.json`，约 2.1 万条，单字）：`word`=汉字，`phonetic`=拼音（多音字用 `/` 分隔），`translation`=按读音/义项整理的释义正文，`detail`=JSON（`strokes`/`radicals`/`structure`/`synonyms`/`antonyms`），`definition`/`pos`/`collins`/`oxford`/`tag`/`bnc`/`frq`/`exchange`/`audio` 留空。
   - **汉语词典**（源：`word.json` 主 + `idiom.json` 增强，约 32 万条，词语/成语）：`word`=词语或成语，`phonetic`=拼音，`translation`=释义正文，`detail`=JSON（命中 `idiom.json` 时附带 `source`/`quote`/`story`/`similar`/`opposite`/`usage`/`notice`/`spelling`），其余留空。
3. **查询侧行为**：与英汉/汉英词典一样按 `lang_from`/`lang_to` 参与自动路由——中文输入命中时，汉语词典与汉英词典的结果并列展示（见 4.2.1「语言方向」）。
4. 落地任务见《实施计划.md》Step 2。

### 5.5 词典内嵌图片/音频资源的存储与访问方案

MDict 的 `.mdd`（以及少数第三方打包时附带 `res/` 资源目录的 StarDict 词典包）会带有图片、发音音频等二进制资源，需要在导入与查询链路中一并处理，纳入 MVP 首期：

1. **导入时落盘、不入库**：资源文件本身不适合存进 SQLite（体积可能几十到数百 MB，存 BLOB 会让数据库文件迅速膨胀、拖慢查询），改为解析 `.mdd`/`res/` 后**逐条落盘**到 Volume 目录：
   ```
   {DICTIONARY_STORAGE_PATH}/{dictionary_id}/
   ├── source/        # 原始上传文件（.mdx/.mdd/.ifo/.idx/.dict...），仅供重新解析/追溯，不对外提供访问
   └── res/            # 从 .mdd / res 目录解出的资源文件 + .mdx 同级目录的附属资源，保留原始相对路径结构
       ├── pic/apple.png
       ├── sound/apple.mp3
       └── oxbw.css     # 来自 .mdx 同级目录（不在 .mdd 里）
   ```
   资源路径统一做**规范化**（反斜杠转正斜杠、去掉开头的 `\`或`/`、拒绝包含 `..` 的路径穿越写入），防止恶意词典包写到 `res/` 目录之外。

   **`.mdx` 同级目录的附属资源也要一并复制**（`copy_sibling_resources`）：MDict 的惯例是把样式表、字体、脚本、图片放在 `.mdx` **同级目录**，词条里的 `<link href="oxbw.css">` 与 CSS 里的 `url("SourceHanSerifJP-Regular.otf")` 都按「词典文件所在目录」解析——MDict 客户端就是这么做的。**这些文件通常不在 `.mdd` 里**：实测大辞泉的 `oxbw.css`/`oxbw.js`（两个 `.mdd` 共 76974 个条目里 0 个 css/js）、岩波的 `iwakoku.css`（`.mdd` 里只有个名字对不上的 `contents.css`）、広辞苑的 `gcy.css` 与 6 个 `.otf`、明镜的 `MK3.css`、新世纪的 `xinrihanshuangjie.css`、Weblio 的 `thesaurus.css`（该词典**根本没有 `.mdd`**）全都是磁盘上的同级文件。只解包 `.mdd` 会让它们全部 404，于是词条以无样式渲染——图标回到原始像素（`Audio.png` 75×74、`b276.png` 387×150）、表格丢掉边框，实测 63 部词典全部中招。复制规则：只扫一层目录、只取扩展名在白名单（`.css/.js/.png/.svg/.woff2/.otf/.ttf/...`）里的直接子文件；**刻意不含 Eudic 专有索引（`.db`/`.bix`/`.bin`）与 `.pdf`**——实测这类文件占附属文件总大小的六成（102MB/176MB）却与渲染无关。已存在的同名文件不覆盖（`.mdd` 里那份属于词典容器内、更权威），写入走「临时文件 + `os.replace`」原子替换（补齐存量词典时词典是启用状态、可能正有人在查）。存量词典用 `POST /api/admin/dictionaries/repair-from-source` 补齐，**不需要重新导入**。

   **可跳过**：`.mdd` 常是词典体积的大头（实测某词典库 `.mdx` 合计 3.9GB、`.mdd` 合计 31GB），而图片/发音并非人人需要。从服务器目录导入时可传 `skip_resources: true` 只导入释义：此时**不创建 `res/`、不解包任何资源**，释义里的资源引用也保持原样不改写（见 5.1.1）。代价是查词时没有发音与插图，且因为是按需可选而非全局开关，同一部署里可能同时存在「带资源」和「不带资源」的词典。注意「没有 `res/`」并不能反推「用户勾了 skip_resources」——只有 `.mdx` 没有 `.mdd` 的词典也没有 `res/`，所以补齐任务不以此为依据跳过（`copy_sibling_resources` 会按需建目录）。
2. **对外访问方式**：不对 `DICTIONARY_STORAGE_PATH` 做整目录 `StaticFiles` 挂载（那样 `source/` 原始词典文件会和 `res/` 一起被暴露），改为一条专用路由 `GET /dict-res/{dictionary_id}/res/{resource_path:path}`——路径里的 `res` 是路由字面量而非可控参数，处理函数据此拼接出的真实磁盘路径固定落在对应词典的 `res/` 子目录下，请求方无论如何构造 URL 都到达不了 `source/`；资源路径同样经第 1 点的规范化校验，找不到文件一律 404。最终图片/音频的访问 URL 形如：`/dict-res/{dictionary_id}/res/pic/apple.png`。

   路径解析由 `resolve_resource_file` 承担，除精确匹配外还有两项兜底：**① 剥掉历史坏链接里多出来的 `file:/` 前缀**（见第 3 点）；**② 大小写不敏感查找**——词典大多在 Windows 上打包，词条引用常与 `.mdd` 里的键大小写不一致，实测汉典的图片引用**全部**是小写而实际键是混合大小写（引用 `down/30/305626w1b7f8b.gif`、实际 `305626w1b7F8B.gif`，`down/0` 一个目录里就有一万九千个这种文件），新漢語林2 正好相反（引用 `gaiji/B245.png`、实际小写），两部合计影响整个 `res/` 的引用。Windows 与 MDict 客户端都不区分大小写，Linux 上就是 404——表现为词条里的文字图片成片丢失。实现按目录段逐级解析、每段仍优先精确匹配，索引按目录缓存（`lru_cache(maxsize=16)`，实测 19499 个文件的目录建一次约 4ms/300KB），并设了 3 万条目的上限——The little dict 的 `res/` 顶层有 67.6 万个文件，那种目录直接放弃建索引（结果同样被缓存，代价只付一次）。

   该路由同时返回 `Access-Control-Allow-Origin: *` 与 `Cache-Control: public, max-age=86400`。CORS 头是**必须**的而不是顺手加的：内置资源要在词条 iframe 里被使用（见第 8 点），那个 iframe 的 `sandbox` 不含 `allow-same-origin`，对浏览器而言是独立的不透明源，加载 `@font-face` 与同源 XHR 都算跨域请求，缺了这个头会**静默失败**——表现为词典自带的字体/样式无声失效，排查起来很费时间。资源本身是公开只读的，放开跨域没有额外风险。
3. **释义 HTML 改写（导入时一次性完成，查询时零开销）**：解析 `.mdx` 释义 HTML 时，用正则匹配 `src="..."`、`href="..."` 等属性值，按协议分流后把词典内部相对路径统一替换为 `/dict-res/{dictionary_id}/res/...` 的绝对 URL，替换后的 HTML 直接存入 `dict_entries.definition`。分流规则：

   | 原写法 | 处理 | 原因 |
   |---|---|---|
   | `sound://x` | → `/dict-res/{id}/res/x` | MDict 的音频协议，指向 `.mdd` 里解包出的文件，转成可播放 URL |
   | `file:///x`（`file://x`、`file:\x` 同理） | → `/dict-res/{id}/res/x` | MDict 里「词典资源根目录」的写法，指向 `.mdd` 里的文件——与 `sound://` 同类。实测 7 部词典约 99 万处在用（汉典、千篇汉语词典 2021/2023、说文解字段注、大辭海、朗文 LDOCE5、新世纪日汉双解），全是 `<img src>` |
   | `entry://word` | **原样保留** | MDict 的词条内跳转协议，指向另一条词条而不是文件；由前端点击时拦截并发起新查询（见第 8 点），后端不该把它当路径 |
   | `http(s)://`、`//host`、`www.`、`#锚点`、`data:`、`mailto:`、`ftp:`、`blob:`、`tel:` | 原样保留 | 外部引用或页内引用 |
   | `javascript:` | 原样保留（前端拦截其点击） | 不该把它改成看似可执行的形态，也不该擅自替词典作者删掉 |
   | 带扩展名的相对路径 | → `/dict-res/{id}/res/...` | 词典内部资源 |
   | **无扩展名的裸相对路径** | 原样保留 | MDX 里这种基本都是词条链接的简写，补成 `/dict-res/` 只会得到 404 |
   | 未知协议 | 原样保留 | 保守处理 |

   同时要保留 `?query` 与 `#fragment`（它们不是路径的一部分），并继续拒绝含 `..` 的越权路径。

   **历史遗留**：早期版本把 `entry://`、`sound://` 与实际指向词典资源的 `file:///` 都当成相对路径改写了（`entry://苹果` → `/dict-res/{id}/res/entry:/苹果`、`file:///down/7/x.gif` → `/dict-res/{id}/res/file:/down/7/x.gif`），在真实词典库上实测分别有 5,602,250 / 887,902 / 989,873 条受影响——表现是点击释义里的词跳转不了、发音按钮全部失效、词条里的文字图片成片消失。修好导入代码只对**今后新导入**的词典生效，已入库的行需要用 `python -m app.cli repair-entry-links` 回溯修复（见 8.6）；修复是纯字符串替换，结果与新导入代码对同一份原始释义的产出**逐条一致**（有一项测试专门钉住这一点）。`/dict-res` 路由同时容忍 `file:/` 前缀，所以**不跑修复命令也能正常显示**，修复只是把数据本身清干净。
4. **StarDict 的资源**：StarDict 官方格式本身不含资源容器，纯 `.ifo/.idx/.dict[.dz]/.syn` 导入时不涉及资源处理。部分第三方打包会额外压缩一个约定俗成的 `res/` 目录，**当前版本不支持 zip 包导入**（未实现解压与 zip-slip 防护），这类带资源包的 StarDict 词典暂不能完整导入图片/音频，留作后续增强；纯文本释义的 StarDict 词典不受影响。
5. **ECDICT 的音频**：`audio` 字段本身就是一个可直接播放的外部完整 URL（不是本地资源），無需落盘处理，前端拿到该字段直接作为 `<audio src="...">` 使用即可；网络不可达时前端做静音降级（隐藏播放按钮）。
6. **清理**：删除词典（4.2.1 的「移除」操作）时，`dict_entries` 通过外键 `ON DELETE CASCADE` 一并删除；`{DICTIONARY_STORAGE_PATH}/{dictionary_id}/res/`（解析时提取的图片/音频等派生资源）无条件删除；`source/` 只有 `import_method='upload'` 时才删除——`dicts_dir` 方式的源文件是用户自己放进 `/data/dicts` 的，不属于本应用管理，不代为清理。删除后额外对 SQLite 执行一次 `VACUUM` + `PRAGMA wal_checkpoint(TRUNCATE)` 回收被删词条占用的磁盘空间（否则文件大小不会自动缩小；WAL 模式下光执行 `VACUUM` 不够，文件长度要等 TRUNCATE 模式的 checkpoint 才会真正收缩，这点用真实的 30 万词条导入+删除验证过：文件从导入后的峰值一次性收缩回空库时的基线大小）。
7. **安全**：`/dict-res/*` 只读、无目录浏览（见第 2 点的专用路由设计）；浏览器上传按 `MAX_UPLOAD_SIZE_MB` 校验总大小，并按声明的 `format` 校验文件后缀白名单（如 `format=ecdict` 只接受 `.csv`），防止把任意文件伪装成词典上传；暂不支持 zip 包上传，因此也未实现 zip-slip 防护，见上一点。
8. **释义 HTML 用隔离 iframe 渲染，不直接注入主页面**：早期版本用 `v-html` 把释义注入主文档，实测有三类问题，而且都不是理论风险（用户 63 部词典 / 24,689,367 条）：**11,069,191 条**含 `<link rel="stylesheet">`，而经 `innerHTML` 注入的 `<link>` **是会加载并全局生效的**（这点与 `<script>` 不同）——63 部词典的样式表因此全部灌进应用的全局 CSS 作用域、互相覆盖并把整个界面改坏；**658,154 条**含内联事件处理器（`onclick`/`onerror` 等），注入后会真的执行，而前端把 token 存在 localStorage 里，等于让任意第三方词典文件（下载站来的 MDX）够到凭证（管理端预览那条路更严重，用的是管理员 token）；`<script>` 虽不执行，但也无从约束。

   改为把释义渲染进 iframe：后端把释义包成完整 HTML 文档（`services/entry_render_service.py`，释义本身是完整文档时不套壳，改为把引导内容插到它自己的 `<head>` 之后，避免嵌套 html 触发怪异模式），前端用 axios 带 token 取回后赋给 `srcdoc`。几个关键选择：

   - **`sandbox="allow-scripts"`，不加 `allow-same-origin`**：两者同时给时框架内脚本能拿到 `window.frameElement`、摘掉 `sandbox` 属性后重载自己，等于逃逸。不加 `allow-same-origin` 时它是一个独立的不透明源，既跑得了词典自己的 JS，又碰不到父页面的任何东西。
   - **注入一段引导脚本**（`services/iframe_bootstrap.js`，排在词典自带脚本之前）承担四件事：① 补齐不透明源下会抛异常的能力（`localStorage`/`sessionStorage` 的内存实现、`document.cookie`、`history.pushState`、`window.open` 转发给父页）；② 把文档高度 `postMessage` 给父页（父页读不到 `contentDocument`），用 `ResizeObserver` + `MutationObserver` + 加载事件 + 有上限的尾部轮询，带 2px 迟滞避免与 `height:100%` 类排版互相触发；③ 拦截 `entry://` 词条跳转（转成消息交父页发起新查询，**同时兼容历史遗留的 `/res/entry:/` 坏写法**，这样修复命令跑之前那些链接就已经能点）与 `sound://` 发音（`.mp3` → `.opus` → 原文件逐个试，见第 9 点）；④ 把外链、`target="_top"`、危险协议收敛到受控路径（无 `allow-popups` 时 `target="_blank"` 是无效的，外链必须转发给父页开新标签）。
   - **父页用 `event.source === iframe.contentWindow` 认证消息**：不透明源发出的 `event.origin` 恒为 `"null"`，按 origin 判断没有意义；另外按帧限流、高度 clamp、连续异常增长则冻结成可滚动。
   - CSP 只声明与 `sandbox` 属性一致的 `sandbox allow-scripts`（属性被误删时仍兜一层），**没有**加资源级 CSP：不透明源下 host-source 的匹配语义不确定，写错会把词典的图片/字体全部拦掉，风险大于收益。
   - **暗色适配**（v1.38 新增，v1.40 扩展）：分两层。① 样式层：`_head_snippet` 里注入一段门控在 `html[data-mydict-theme='dark']` 下的 CSS，**只翻「明确写着黑/白」的呈现**（`<font color="#000">`、内联 `style` 的 `color:#000` / `background:#fff`），词典自带的红字、彩色表格等语义色一律保留。② 运行时提亮：写死的颜色值五花八门（深蓝最常见），CSS 属性选择器枚举不完，而 CSS 自己也**算不了亮度**——所以引导脚本在暗色下扫一遍正文，读每个元素的计算颜色，亮度低于阈值的**按同色相提亮**（`hsl(from <原色> h s 66%)`，蓝的还是蓝的，只是变亮），并记录原值以便切回浅色时还原；灰阶的深色（纯黑/深灰）不在这里处理，交给样式层用主题前景色统一替换。相对颜色语法不被支持时整段跳过；元素数超过 5000 只处理前一批，避免大词条卡顿。主题有两个来源：① 请求参数 `theme`（三个 entry 端点新增，前端在 api 层统一带上）由服务端直接写进文档，消除「先按系统偏好渲染、等父页消息到达才变色」的首屏闪白；② 运行中切换走既有的 `mydict:cmd {cmd:'theme'}` 下行通道，**不重建 iframe**——`EntryPanel` 特意保留已挂载的 iframe，重建会丢音频播放位置与内部滚动。样式在渲染时注入、不改库里的 `definition`，因此新导入的词典自动适用。

   **残余风险（如实记录）**：`allow-scripts` 挡不住 CPU 空转、消息刷屏、以及通过动态 `<img>`/`<script>` 把数据外发出去；不透明源下 Web Worker、同源 XHR、表单提交、`download` 属性、`alert` 弹窗也受限。这些需要在真实词典上逐部实测评估。
9. **发音播放**：三种来源——`.mdd` 里解包出的音频（`sound://` 链接，见第 8 点）、ECDICT `audio` 字段的外部 URL、以及词典自带的播放 JS。
   - **`.mp3` 等常见格式**浏览器原生可播，直接播放。
   - **`.spx`（Speex）浏览器全都不支持**，而用户库里这类有 988,623 个（「NHK日本語発音アクセント辞書」的 152,806 条发音全是它，发音就是这部词典的全部意义）。处理方式是**离线转码**：`scripts/transcode_spx.py` 在同目录生成 `.mp3`（默认；也可选 `.opus`）并保留原文件，前端按 `.mp3` → `.opus` → 原文件的顺序逐个尝试，所以部分转码也能用。ffmpeg 的发行版构建通常是 GPL/LGPL，**不装进镜像**（与本项目 MIT 授权不兼容），脚本在宿主机或一次性容器里跑。实测默认参数下单文件 0.055 秒、产物约为原始体积的 1.44 倍，全量约 6.5GB。
   - 另有三条并行路径（v1.42 / v1.43）：**播放时按需转码**（前端来要 mp3 而它不存在时，`/dict-res` 现场转一个落盘，实测约 60ms，下次直接命中）、管理后台的**词典管理 → 批量转码**（走后台任务，单部与批量同一个端点），以及继续用离线脚本预转。三者互不冲突——转好的产物都会被直接命中。判「已经转好」的口径统一为**同名同目录下存在非空 `.mp3` 或 `.opus`**（必须同名同目录：韦氏大学词典与 The little dict 自带的 mp3 在别的目录，按「目录里有 mp3」判会整体误判）。
   - **批量转码成功后删掉原 `.spx`**（离线脚本要显式加 `--prune-source` 才删）。这是有意的取舍：源词典文件另有备份，而留着会让磁盘同时承担两份音频。代价是删源后不可再生——若日后 mp3 损坏，只能从源词典重新导入来恢复发音。

## 6. 限流与缓存设计

- **Token 按日限流**：直接以 `query_stats_daily` 当日行的 `query_count` 作为计数器——每次请求先读该 Token 当天的行，未超 `daily_limit`（为空则取系统默认 `token_default_daily_limit`）则 `query_count+1` 并放行，否则 `rate_limited_count+1` 并返回 `429`。按日计数天然需要跨进程重启保留状态，用 DB 行本身当计数器比另外维护一份内存态、定期异步落库、重启再预加载要简单可靠：写一次即是持久化，重启后读到的就是最新值。计数器的键是**本地日期**，因此配额在**本地零点**重置；`429` 的 `Retry-After` 也按下一个本地零点计算（此前误按 UTC 零点算，会多报一个时区偏移）。
- **按 IP 按分钟限流**：进程内内存计数器（`{key}:{minute_bucket}` → 次数，TTL 略长于 1 分钟自动过期）。匿名场景 `key = anon:{ip}`，对应 `anonymous_ip_rate_limit_per_min`，覆盖 `open_access=true` 时的匿名 Web 访客与匿名 API 调用；登录用户 Web 查询场景 `key = user:{ip}`，对应 `user_ip_rate_limit_per_min`，与登录态无关的 `open_access` 开关（登录用户始终鉴权通过，不受该开关影响），两套计数器 key 前缀不同，同一 IP 下登录/匿名请求互不占用对方配额。窗口很短，重启丢失可接受，不需要数据库持久化。
- **查询结果缓存**：TTL 缓存（5 分钟），Key 为 `word_lower + 参与匹配的词典 id 集合`，减少高频重复查询对 SQLite 的读取压力；词典启用/禁用/导入/删除时整体清空缓存（不做按词典粒度的精细失效）。
- **统计聚合任务**：APScheduler `BackgroundScheduler` 每 10 分钟运行一次，把 `query_logs` 中 `token_id` 为空的记录（登录用户 Web 查询 + 匿名 Web/API 调用）按「用户」「匿名」两个维度重新聚合、覆盖写入 `query_stats_daily`（`token_id`/`user_id` 均为空的行代表匿名维度）；Token 维度已由上述按日限流环节实时写入同一张表，聚合任务不重复处理，避免两套写入逻辑互相覆盖。聚合按**本地日**划分（用本地日的 UTC 区间取日志，边界换算见 `core/timeutil.py`），与写进 `stat_date` 的本地日期标签口径一致——此前用 `func.date(created_at)` 是按 UTC 日分组，标签与内容会错开一个时区偏移。为保证限流也能被事后统计到，匿名调用被限流时同样写一条 `status='rate_limited'` 的 `query_logs`（Token 被限流已直接体现在 `query_stats_daily.rate_limited_count` 里，不重复记日志）。
- **query_logs 写入范围**：成功/未命中只记 `GET /api/v1/query`（第三方 API）与 `GET /api/dict/search`（Web 端）两个实际查词接口（每次请求一条，`dictionary_id` 取命中的第一个词典，未命中为空）；`suggest`（联想）与 `dictionaries`（词典列表）不计入成功量，避免联想输入的高频击键或元数据拉取污染查询统计。但三者（`query`/`suggest`/`dictionaries`）的**匿名调用被限流**时都会额外写一条 `status='rate_limited'` 的记录，供统计聚合任务还原匿名维度的限流次数；`/api/dict/search` 登录用户被 `user_ip_rate_limit_per_min` 限流时同样写一条带 `user_id` 的 `rate_limited` 记录，聚合进该用户维度。
- **后台任务可见性与导入异步化**：`services/background_task_service.py` 是一个进程内、线程安全的登记表（不持久化、不跨进程），词典导入开始时登记一条任务、每批（2000 条）写库后更新已处理数，结束时写入终态（`success` 带 `result={dictionary_id, word_count}`，`error` 带可读错误信息）并保留 10 分钟供轮询方读取、之后清理。两个用途分开消费同一张表：① `GET /api/admin/tasks/running` 只返回 `status=running` 的任务，管理后台顶栏每 5 秒轮询一次，让别的标签页/会话也能看到"正在导入"；② `GET /api/admin/tasks/{task_id}` 返回单个任务的完整记录（含终态），发起导入的客户端凭 `start_dictionary_import()` 返回的 `task_id` 轮询它，直到 `success`/`error` 才认为导入真正完成——早期版本导入是同步跑完才返回响应，大词典解析耗时超过前端 axios 10 秒超时后请求被客户端中断、界面显示"没反应"，但后端并未取消、最终仍会导入成功，只是响应没能在超时前送达；改成 `start_dictionary_import()` 校验完参数立即用 `threading.Thread` 派发解析入库、马上返回 `task_id`，从根源上避免了这个问题，`POST /api/admin/dictionaries`（浏览器上传）与 `POST /admin/dictionaries/import-from-dicts-dir`（服务器目录导入）都不再需要靠 `run_in_threadpool`/线程池来避免独占事件循环。

## 7. 前端样式架构（结构化样式定义）

对应《UI设计规范.md》定义的设计原则（简洁统一、立体、清新、浅深双主题），本节给出这些视觉规则在代码里落地的**结构化方案**，目标是"改一处 Token、全站生效"，避免样式散落在各组件里难以统一调整。

### 7.1 技术选型：CSS 自定义属性作为 Token 运行时载体

不引入 Tailwind（与已选定的 Element Plus 组件库定位重叠，两套原子化/组件化方案混用容易冲突），而是用**原生 CSS 自定义属性（CSS Variables）**承载 Design Token，配合 Vite 的 CSS 处理即可，无需额外的 CSS-in-JS 或 SCSS 编译链：

- 所有 Token 以 `--` 前缀的 CSS 变量定义在 `:root`（浅色默认值）。
- 深色主题通过属性选择器 `:root[data-theme="dark"]` 覆盖同名变量，组件样式全程只写 `var(--token-name)`，不感知当前是什么主题——**主题切换=换一份变量取值，组件代码零改动**。

### 7.3 主题切换机制

- 状态管理：`composables/useTheme.ts` 提供 `theme: 'light' | 'dark' | 'system'`、`resolvedTheme`（实际生效的 light/dark）、`setTheme()`；初始值读取 `localStorage`，未设置过则取 `window.matchMedia('(prefers-color-scheme: dark)')`。
- DOM 应用：`watchEffect` 里执行 `document.documentElement.setAttribute('data-theme', resolvedTheme)`，CSS 侧 `:root[data-theme="dark"]` 选择器随之生效；`system` 模式下额外监听 `matchMedia` 的 `change` 事件跟随系统切换。
- 持久化：用户手动选择后写入 `localStorage('mydict-theme')`，优先级高于系统偏好；访客/未登录同样生效（纯前端行为，不依赖登录态）。
- 过渡动画：`transition.css` 里对 `background-color`/`border-color`/`color`/`box-shadow` 统一设置 `transition: var(--motion-duration-fast) var(--motion-ease-standard)`（如 150ms），仅作用于这几个属性，避免布局属性也被过渡导致切换时页面"抖动"。

### 7.4 与 Element Plus 主题联动

管理后台复用 Element Plus 组件，其本身通过一套 `--el-*` CSS 变量支持运行时主题定制。`element-plus-theme.css` 把我们的 Token 映射过去，例如：

```css
:root {
  --el-color-primary: var(--color-brand-500);
  --el-color-primary-light-3: var(--color-brand-300);
  --el-border-radius-base: var(--radius-md);
  --el-bg-color: var(--color-bg-surface);
  --el-bg-color-overlay: var(--color-bg-surface-raised);  /* popover/下拉/select/日期面板等悬浮层背景，独立变量，容易漏映射 */
  --el-text-color-primary: var(--color-text-primary);
  --el-border-color: var(--color-border);
  /* 完整映射（含 fill-color、各级 border-color/text-color）见 element-plus-theme.css */
}
```

深色取值不需要单独写一份 `[data-theme="dark"]` 覆盖——右边这些 `--color-*` 自有 Token 本身已经在 `color.css` 里按主题分别定义好了，`--el-*` 只是引用同一个变量名，主题切换时自动跟着变。

这样管理后台里直接使用的 `<el-button>`、`<el-table>`、`<el-popover>` 等组件无需逐个定制样式，颜色/圆角/主题切换自动跟随全局 Token。**踩过的坑**：`--el-bg-color` 只控制页面级背景，`el-popover`/`el-dropdown`/`el-select`/`el-date-picker`/`el-message` 等悬浮层组件走的是另一个独立变量 `--el-bg-color-overlay`，漏映射这一个就会导致深色模式下这些组件背景仍然是亮的（其余组件正常）——新增 Element Plus 组件用到悬浮层时，先确认它消费的是不是这个变量。

### 7.5 使用约束（配合《代码规范.md》）

- 业务组件的 `<style scoped>` 中只允许出现 `var(--token-name)` 形式的取值，禁止硬编码颜色/像素数值；确需一次性特殊值时须加注释说明原因，便于后续 Review 识别。
- 新增视觉规则（新色阶、新阴影层级等）一律先更新《UI设计规范.md》与本节 Token 表，再落到 `styles/tokens/` 对应文件，保持"文档定义 → 代码实现"的单向可追溯性，避免代码里出现文档没记录的"野生 Token"。

### 8.2 单一镜像构建（多阶段 Dockerfile）

```dockerfile
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1"]
```

FastAPI 侧路由挂载顺序：先注册 `/api/*` 各路由，再用 `app.mount("/", StaticFiles(directory="static", html=True), name="static")` 兜底；对不存在的静态文件路径统一 fallback 返回 `index.html`，以支持 Vue Router 的 history 模式前端路由。

`docker-compose.yml` 仅需一个 `app` 服务（映射端口、挂载 `./data:/data`、可选读取 `.env`），也可以不使用 compose，直接：

```bash
docker build --build-arg GIT_BRANCH=$(git rev-parse --abbrev-ref HEAD) -t poxenstudio/mydict .
docker run -d -p 8000:8000 -v $(pwd)/data:/data poxenstudio/mydict
```

`.git` 目录不在构建上下文里（见 `.dockerignore`），分支名必须由构建方显式传入 `--build-arg`；不传时 `GIT_BRANCH` 落回 `dev`，与 `/version.txt` 缺失/不可读时后端的兜底值一致。

无需 `frontend`/`db`/`redis` 独立服务，一个容器即可完成整套部署。

### 8.3 关键环境变量（`.env`，可选）

所有变量均有等价默认值，`.env` 文件本身不是必需的；`docker-compose.yml` 中 `env_file` 标记为 `required: false`，缺省时直接用内置默认值启动。

```
# JWT_SECRET=                                  # 留空则首次启动自动生成，持久化到 /data/config/jwt_secret.key
# OPEN_ACCESS_DEFAULT=false
# ALLOW_REGISTRATION_DEFAULT=true
# TOKEN_DEFAULT_DAILY_LIMIT=1000
# ANONYMOUS_IP_RATE_LIMIT_PER_MIN=60
# MAX_UPLOAD_SIZE_MB=512
# ENABLE_SCHEDULER=true                        # 统计聚合定时任务开关，仅测试环境需要关闭
# CONFIG_STORAGE_PATH=/data/config
# DICTS_INBOX_PATH=/data/dicts                 # 待导入词典源文件目录，见 5.1.1「从服务器目录导入」
# DATABASE_PATH=/data/db/mydict.sqlite3
# DICTIONARY_STORAGE_PATH=/data/dictionaries   # 已导入词典的归档与对外资源目录
# LOG_DIR=/data/logs                           # 运行日志目录，按 5MB/5 份自动滚动
```

> `JWT_SECRET` 若显式设置则优先使用（便于多副本/重建镜像时保持会话有效）；若留空，首次启动生成随机密钥并写入 `/data/config/jwt_secret.key`，随 Volume 持久化，容器重建后仍能复用、已签发的登录态不会失效。

### 8.4 首次启动流程

1. `docker run`（或 `docker compose up -d`）启动单个容器，backend 启动时自动执行数据库迁移（Alembic，对 SQLite 文件建表/升级）。
2. 访问 `http://<host>/admin`，检测到未初始化管理员 → 跳转 `setup` 页设置管理员用户名/密码。
3. 登录后台 → 导入词典（MDict/StarDict/ECDICT）→ 启用 → 创建 Token 交给第三方 / 前台即可查询；如需允许游客/免 Token 查询，在「系统设置」中打开「开放使用」。

### 8.5 管理员密码重置（无邮件服务场景）

提供一个后端管理命令（如 `python -m app.cli reset-admin-password`），通过 `docker exec` 进入 backend 容器执行，直接以命令行方式重置管理员密码，作为忘记密码时的兜底方案。

### 8.6 其它运维命令

历史遗留数据的修正无法在启动时自动完成（要么耗时长、要么会覆盖人工设置），一律做成**需要显式执行**的命令，默认拒绝对数据的写入：

- **`python -m app.cli repair-entry-links [--dictionary-id N] [--batch-size 5000] [--dry-run] [--yes]`**
  修复早期被误改写的 `entry://` / `sound://` / `file:///` 链接（见 5.5 第 3 点）。按**主键区间**分批 UPDATE —— 用 `(dictionary_id, word)` 唯一索引反而会因为排序是 word 导致每批都重扫；行内用 `replace()` 就地改写，前缀里带词典 id，不可能跨词典误改。`file:/` 那一条实测影响 7 部词典约 99 万行（汉典、千篇汉语词典 2021/2023、说文解字段注、大辭海、朗文 LDOCE5、新世纪日汉双解），不跑也能显示（`/dict-res` 路由容忍该前缀），跑了则是把数据本身清干净。跑完需重启应用容器：查询结果缓存在服务进程内存里，CLI 作为独立进程清不到它。

- **`python -m app.cli redetect-languages [--dictionary-id N] [--dry-run] [--yes]`**
  按当前采样逻辑重新识别词典的语言方向（见 5.1）。**必须单独跑**：采样逻辑改好只影响今后导入的词典，已入库的 `lang_from` 不会自动更新，而查询路由依赖它（4.2.3 的软过滤只在「优先语言一部都没命中」时才兜底，救不了这种情况）。只覆盖识别出结论的那一侧，识别不出来时不动现值。

- **`scripts/transcode_spx.py --root <资源目录>`**（Python 脚本，不走 `app.cli`）
  把 `.spx` 发音离线转成可播放音频（见 5.5 第 9 点）。它是运维工具、不属于运行时代码，因此不随镜像分发；需要宿主机有 ffmpeg。支持 `--dry-run`、`--limit`，幂等（已有产物默认跳过）。

## 9. 安全设计要点

- 密码：bcrypt 哈希 + salt。
- Token：仅存哈希值（SHA-256），创建/重新生成时一次性展示明文，之后不可再获取完整值。
- 管理员与普通用户 JWT 使用不同 `aud`/scope，互不可用；Token 生词本与用户生词本数据表完全隔离，避免越权访问。
- 上传词典文件做大小校验（`MAX_UPLOAD_SIZE_MB`）与文件后缀白名单校验（按声明的 `format` 限定可接受后缀），存储路径与 Web 可访问目录隔离（见 5.5 节第 2 点），防止任意文件访问/路径穿越；服务器目录导入的文件名同样做白名单校验，拒绝 `/`、`\`、`..`。
- 解析器对文件完整性的校验统一转换为 4xx 业务错误（而非未处理异常导致的 500），管理员能看到具体原因（如"缺少必要文件""文件类型不匹配"）。
- API 查询与收藏接口按 Token 每日限流、Web 端按 IP 每分钟限流，超限返回 `429`。
- 所有管理操作（词典导入/删除/启用禁用、Token 创建/禁用、用户禁用/重置密码、系统设置变更）写入 `audit_logs`。
- 管理员/用户登录成功与失败均通过标准 `logging` 输出（成功 INFO 级含用户名与 id，失败 WARNING 级含尝试的用户名）：同时写 stdout（随容器日志可直接 `docker logs` 查看）与 `LOG_DIR`（默认 `/data/logs/mydict.log`）滚动文件（`RotatingFileHandler`，单文件 5MB、保留 5 份），不落库，仅用于运行时排障，不作为合规审计凭证（合规审计见上一条 `audit_logs`）。
- 词典释义 HTML **不直接注入主页面**，改为渲染在 `sandbox="allow-scripts"`（不含 `allow-same-origin`）的隔离 iframe 里（见 5.5 第 8 点）——词典文件是第三方产物，其内联事件处理器在主页面下会真的执行，而 token 存在 localStorage 里。父页只接受 `event.source` 匹配的消息，不解析消息内容为代码。
- 词条渲染端点（前台 `/api/dict/entry/{id}`、管理端 `/api/admin/dictionaries/{id}/entry`、生词本 `/api/vocab/{id}/entry`）都要求有效身份：前台那条还要校验词典已启用且在该调用方的「可用词典」范围内，不满足时统一 404，不泄漏词典是否存在。前端必须用 axios 带 token 取回再赋给 `srcdoc`——若让 iframe 直接 `src` 导航过去，请求不带 `Authorization` 头，端点就只能匿名开放、绕过「可用词典」限制。
- 查询的 `dict=` 参数与「检索范围」侧边栏只能**收窄**范围，仍与 Token/用户的「可用词典」取交集；侧边栏勾选只写本地存储，不提供任何改词典启用状态的路径（那是管理端权限）。
- 已知未覆盖项（当前部署规模下可接受，后续如需加固可补充）：容器内以镜像默认用户（root）运行，未切换非 root 用户；StarDict 的 zip 资源包导入未实现（见 5.5 节第 4 点）；隔离 iframe 拦不住 CPU 空转、消息刷屏与通过动态子资源外发数据（见 5.5 第 8 点的残余风险）。
