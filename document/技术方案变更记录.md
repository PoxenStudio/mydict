## v1.53

**发音方案切换：去掉服务端 Speex 转码，改为前端 JS 解码**。此前认为
「浏览器都不支持 .spx，必须转成 mp3」——前半句对（Chrome/Safari/Firefox 的原生解码器
都没有 Speex），后半句不对：libspeex 可以编译成 JavaScript 在浏览器里解，django-mdict
项目正是这么做的（`speex.min.js` + `bitstring.min.js` + `pcmdata.min.js` 共约 320KB，
链路是 XHR 拿 spx 字节 → Ogg demux → `Speex.parseHeader` 取 mode/rate/声道 → 解出 PCM →
`PCMData.encode` 合成 WAV Blob → 原生 `<audio>` 播放，连 Web Audio API 都不用），实测
可用。改为同样的路线：解码器三件套随前端静态资源分发（`frontend/public/speex/`，
libspeex 为 BSD 许可），引导脚本在转码候选（.mp3/.opus，词典原生自带的照常直接播）
都落空后 fetch 原 .spx 交给解码器；二进制转字符串必须分块（`String.fromCharCode.apply`
参数个数有上限）；沿用 django-mdict 的经验修正——双声道时采样率减半，否则 NHK 的
32kHz 双声道 spx 播放过快。随之移除整套服务端转码：`spx_transcode.py`、`/dict-res` 的
按需转码钩子、`/admin/dictionaries/scan-spx` 与 `/transcode-spx` 端点、设置页的 ffmpeg
面板与 `spx_online_transcode` 开关、离线脚本 `scripts/transcode_spx.py`；ffmpeg 不再是
任何形式的依赖。`dict_entries` 的 `spx_pending_count`/`spx_scanned_at` 两列保留
（删列需要再一次 29GB 整表重建，不值得），但不再写入、不再对外暴露。已有的 mp3 全部
保留（其中约 10.5GB 是词典原生自带的真人发音，与新方案天然兼容；NHK 那 14 万个转码
产物现在是该批发音的唯一副本，删除 spx 的原文件已无法恢复，除非对该词典跑「重新解析」）。

## v1.52

**修复静默丢数据：同一部词典允许存在多条同名词条**。`dict_entries` 原有
`UNIQUE(dictionary_id, word)` 约束，导入时同名只留首条（`_batch_insert` 的 `seen_words`）。
设计意图是处理 StarDict `.syn` 别名冲突——那种情况两条内容完全一样，丢一条无所谓；但
**MDict 允许同一词头有多条内容不同的条目**（搜韵诗词全文检索版的「毛泽东」有 82 条，
是 82 首不同的诗词），实测 63 部词典里 49 部受影响，共静默丢失 **1,445,181 条**
（源 26,134,548 条 → 只入库 24,689,367 行），且不报错、也不体现在 word_count 里。
这是上游的原始设计（git blame：3ef05121 / 080442dc，2026-09-10），不是本分支引入的。
改动：① 迁移 `e5b7c9d1a3f4` 去掉唯一约束（SQLite 上是 autoindex、无法单独 DROP，
batch_alter_table 整表重建），并补 `(dictionary_id, word_lower)` 复合索引——查询按这两列
过滤，而原唯一索引建在 `(dictionary_id, word)` 上（word 非 word_lower），对查询本来就
使不上力；② 导入不再去重；③ 查询结果带条目 id（`schemas/query.py` 的 QueryResultItem
同步加字段）；④ **词条端点聚合渲染**：同一词典里匹配这个词（含变体）的全部条目合成
**一个** HTML 文档返回，条与条之间有小标题（序号/词头/注音）与分隔线——逐条各建 iframe
的话，搜韵展开一次要挂载 82 个沙箱文档；只传一条时输出与旧版逐字节一致；前端多条时
整组只用一个 iframe。前端把查询结果里那一组的条目 id 显式传给端点（`entry_ids`），
保证 iframe 里的条数与「共 N 条」一致——按 word 再推一遍变体集合可能对不上（查询用的
是用户输入推的变体，词头是词典自己的写法）。生词本**不受影响**：收藏按 `(user_id, word)`
唯一，与词典无关；`/{item_id}/entry` 渲染的是收藏时存的快照。⑤ 存量数据靠新增的
`POST /admin/dictionaries/reparse`（词典管理页「重新解析」按钮）：重读源文件、把词条
整个重灌一遍——**词典 id 不变**（Token/用户白名单、生词本、检索范围勾选都不用重配；
词条 id 会变，但没有数据引用它）。刻意做全量重灌而不是只补缺失行：此前有几轮导入期改写
修复（资源引用改写、StyleSheet 展开），老行是老规则产出的，只补缺失会把新旧两种格式混在
同一部词典里；失败重跑即可，每次都从清空开始。源文件不在的词典跳过并计数。

## v1.51

去掉词条 iframe 里的滚动条：根因是词典用**负外边距做「出血」**——千篇汉语
词典是 `ul{margin:-12px -6px 0}`，左右各溢出 6px。这 6px 会引出**两根**滚动条：横向那根
占掉约 15px 视口高度，于是内容又纵向溢出，纵向那根跟着出现——所以「宽度和高度都有滚动条」
其实是同一个根因。修法是给注入的文档加 `html{overflow-x:clip}`：用 `clip` 而不是 `hidden`，
因为 `hidden` 会让 html 变成滚动容器（连带影响 position:sticky）。实测各词典在 760px 视口
下的横向溢出量：千篇恒为 6px，大辞泉/辞海/広辞苑/明镜/Weblio/大辭海全为 0，都是装饰性出血、
裁掉不丢内容。用 headless Chrome 做了 A/B 对照：去掉这行时横向滚动条出现（`clientHeight`
比 `innerHeight` 少 15px），加上后消失。

## v1.50

两处：① **暗色下过亮的背景自动压暗**——此前只做了「提亮过暗的文字」，但词典
同样常把背景写死成浅色（千篇汉语词典的正文容器 `.mcon` 就是 `#ebeee9`），浅底配被提亮的
浅字等于什么都看不见。补上对称的一半：运行时读计算背景色，太亮就按**同色相压暗**
（浅绿底变深绿底）——刻意不用 `transparent`，那会把 `<hr>` 这类靠背景色显示的分隔线一起
弄没；顺带在暗色样式里补 `background-image:none`，因为词典常写 `background:#f2f3ee
url(bg.jpg)` 这样的简写，只翻 `background-color` 的话那张浅色底图还在。② **词条高度上限
放宽**：iframe 的高度上限 12000 → 120000、增长守卫由「3 秒内增长 5 次」放宽到「5 秒内
40 次」。两者都会在长词条上把 iframe 冻成内部可滚动，表现就是「高度没自适应 + 词条里出现
滚动条」；放宽守卫是因为**图片解码本来就会让高度一路变大**——千篇那类词条有一千多张字形
图，每张解码完触发一次上报，按原阈值会把正常的加载过程误判成布局震荡。

词条内点击大图弹出大图查看器。起因是扫描版词典——辞海（id=26）每个词条的正文
就是一整页扫描图 `<img src="/dict-res/26/res/CHHDB_0121.jpg" width="100%">`，天然尺寸

`stopImmediatePropagation`）。单张查看、不做翻页：辞海翻页本来靠词条里的「上一葉/下一葉」
链接，点了会重新查词。

## v1.47

展开 MDict 的 `` `编号` `` 样式标记。`.mdx` 头部的 `StyleSheet` 字段定义了
「编号 →（开始标签, 结束标记）」的替换表——每个编号占三行（`mdict_utils` 的 `readmdict.py`
里有权威说明：`style_number # 1-255` / `style_begin` / `style_end`），正文里写 `` `编号` ``
来引用。此前这个字段完全没被读过，于是标记原样显示出来，看起来就是排版错乱：
多功能汉语辞典和高级成语词典**全部 101653 条**中招、日本語表現文型辞典 488 条。展开规则是
**遇到标记时先补上一个标记的结束标记、再输出当前的开始标签**，文末补上最后那个待补的
结束标记——只输出开始标签是不行的，`` `1` `` 是 `<b><center><font size=5 color=Green>`，
只开不关会把整条词条都居中加粗；而 `` `10` `` 这类标记出现在上一行行尾、样式是给下一行
正文用的，也不能靠「换行即闭合」偷懒。**只替换样式表里定义过的编号**：同库里另有 3 部
词典（优词词源、Vocabulary.com、俚语 Urban Dictionary）正文恰好含反引号数字但它们的 mdx
没有 `StyleSheet`，是巧合文本，绝不能误伤。纯文本扫描、不解析 HTML（与 MDict 客户端一致）：
理论上标记若出现在属性值里也会被展开，但真实语料里 0 命中，不为它加属性值区间判断。
导入时在**资源改写之前**展开，这样样式表标签里自带的 `src` 也会被一并改写成 `/dict-res/…`。
存量数据不必重新导入：`POST /api/admin/dictionaries/repair-from-source`（原 `repair-resources`
扩成「从源文件修复」，一次把「补齐 `.mdx` 同级附属资源」与「展开样式标记」两件事都做了，
页面按钮同名）。关键约束是**不能每部词典都打开 `.mdx`**——`MDX.__init__` 会把整份词头索引
读进内存，实测 63 部全开要 60~80 秒（搜韵诗词 17.6s、The little dict 8.7s），还有个别是
LZO 压缩根本打不开，所以先用一次 LIKE 扫描定位「词条里真的含反引号」的少数几部，只对它们
打开源文件。生词本里已收藏的释义**快照不动**——快照的语义就是「收藏当时的样子」。

## v1.46

修 `file:///` 资源引用与资源路径大小写。词条里的文字图片成片丢失，两个根因：**①** MDict 用 `file:///down/7/x.gif` 表示「词典资源根目录下的文件」，与 `sound://` 同类，而早期改写把这个协议也当成普通相对路径拼成了 `/dict-res/{id}/res/file:/down/7/x.gif`（实测 7 部词典约 99 万行：汉典、千篇汉语词典 2021/2023、说文解字段注、大辭海、朗文 LDOCE5、新世纪日汉双解，全是 `<img src>`）；`file:` 后来进了「原样保留」名单，于是新导入的词典又把 `file:///…` 原样留下，浏览器同样打不开——两头都是坏的。现在改写为 `/dict-res/{id}/res/…`（`file:` 后面的两三个斜杠、正反斜杠都吃掉），`/dict-res` 路由同时容忍历史遗留的 `file:/` 前缀，所以**不必跑修复命令就能显示**。**②** 词典多在 Windows 上打包，词条引用与 `.mdd` 里的键大小写常不一致：汉典的图片引用**全部**是小写而实际键是混合大小写（引用 `down/30/305626w1b7f8b.gif`、实际 `305626w1b7F8B.gif`，`down/0` 一个目录就有一万九千个这种文件），新漢語林2 正好相反（引用 `gaiji/B245.png`、实际小写）；Windows 与 MDict 客户端都不区分大小写，Linux 上就是 404。`resolve_resource_file` 因此逐段做大小写不敏感兜底（每段仍优先精确匹配），索引按目录缓存（`lru_cache(maxsize=16)`，19499 个文件的目录建一次约 4ms/300KB），并设 3 万条目上限——The little dict 的 `res/` 顶层有 67.6 万个文件，那种目录放弃建索引。`repair-entry-links` 顺带把 `file:/` 也纳入修复；后端 pytest 301 passed。

## v1.45

导入时复制 `.mdx` 同级的附属资源。MDict 的惯例是把样式表、字体、脚本、图片放在 `.mdx` **同级目录**：词条里的 `<link href="oxbw.css">` 与 CSS 里的 `url("SourceHanSerifJP-Regular.otf")` 都按「词典文件所在目录」解析。**这些文件通常不在 `.mdd` 里**——实测大辞泉的 `oxbw.css`/`oxbw.js`（两个 `.mdd` 共 76974 个条目里 0 个 css/js）、岩波的 `iwakoku.css`、広辞苑的 `gcy.css` 与 6 个 `.otf`、明镜的 `MK3.css`、新世纪的 `xinrihanshuangjie.css`、Weblio 的 `thesaurus.css`（该词典根本没有 `.mdd`）全都是磁盘上的同级文件，而早先的导入代码只认 `.mdx`/`.mdd`，于是它们全部 404，词条以无样式渲染——六个用户报来的症状（Weblio 表格看不出是表格、大辞泉发音图标 75×74、岩波派生語图标 387×150、広辞苑【形】括号、新世纪与明镜的三角标）**全是这一个根因**，实测 63 部词典全部中招。改为导入时用 `copy_sibling_resources` 把同级目录里的附属文件一并复制进 `res/`：只扫一层、只取白名单扩展名（`.css/.js/.png/.svg/.woff2/.otf/.ttf/...`），**刻意不含 Eudic 专有索引（`.db`/`.bix`/`.bin`）与 `.pdf`**——实测这类文件占附属文件总大小的六成（102MB/176MB）却与渲染无关；已存在的同名文件不覆盖（`.mdd` 里那份更权威），写入走「临时文件 + `os.replace`」原子替换。上传通道的白名单同步放宽，浏览器上传也能带配套 CSS/字体。存量词典用新增的 `POST /api/admin/dictionaries/repair-resources` 补齐（词典管理页「补齐附属资源」按钮，后台任务，**不需要重新导入**——大辞泉有 95 万词条，重导代价太大）。
